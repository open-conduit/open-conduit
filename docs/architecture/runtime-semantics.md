# Routing, waits and recovery semantics

Decision B04 · ticket 01-04. This resolves the runtime choices left by [B02](domain-storage.md) and [B03](extensions.md). Normative “must” requirements apply to stage 02 implementations. The executable specification is [the shared runtime suite](../../conformance/runtime_cases.go), using [a public test adapter](../../conformance/runtime.go) and [a volatile reference coordinator](../../conformance/reference/runtime.go). Route handlers use [the public extension contract](../../extension/routing.go). No production scheduler, daemon or backend is delivered here.

Run `go test -race ./...`, `go vet ./...` and `go build ./...`. Tests use explicit clocks and channel barriers; wall-clock deadlines only detect a stalled test. The suite must be adapted to the real runtime in 02-03–02-05, then rerun through SQLite reopen and process boundaries in 02-09. Passing this reference does not prove process control, throughput, durability or real service parity.

## Routing and ownership

1. Acceptance durably retains the immutable Event and assigns its sequence before acknowledging ingress. Routing is a separate checkpoint. A duplicate `(source, delivery_id)` returns the original Event without rerunning committed effects. Correlation never substitutes for delivery identity.
2. Trusted ingress configuration selects one target Scope. An explicit Work ID selects that Work and its fixed scope; any supplied correlation must resolve to the same Work. Reject contradictory identity/scope rather than overriding it. Source namespaces include account/resource identity; uniqueness is `(source, external_id)` across scopes, including terminal Work. Matching a route cannot grant cross-scope authority.
3. Resolve effective routes root to leaf. Within a scope, route names must be unique and declaration order is significant. A descendant's same-name route replaces the entire ancestor route in its original slot; new names append. Evaluate in that order and stop at the **first match**, including a match choosing drop. A handler error stops processing without trying later routes. No match commits `unmatched`, retaining the Event. There is no broadcast to every matching handler.
4. Handlers see detached Event/Scope/optional Work snapshots, do deterministic local computation and return decisions. They never call services or write coordination state during matching. A revision conflict requires reread/re-evaluation, with stable proposed IDs. Runtime atomically revalidates ownership and applies create/append-keys, context, queue/intents and `MarkRouted`. No executor launch or remote action runs in that transaction.
5. Concurrent Events resolving to one key create at most one Work. Different keys owned by one Work serialize route effects by **acceptance sequence**, not occurrence time, handler completion or goroutine order. Key attachment and route checkpoint commit together. Attachment adds keys, never removes/transfers them; an owned-by-other key aborts all effects and leaves the Event unrouted for diagnosis/retry. Acquire multiple key/Work guards in canonical order or use equivalent transactional conflict handling.
6. On key attachment, earlier accepted, still-unrouted Events for the new key join that Work's ordered backlog. Already checkpointed `unmatched`, `drop` or `terminal` Events stay checkpointed; attachment never silently resurrects them. An operator can emit a distinct, causally linked replay-request Event. Previously unresolved Events do not acquire a retroactive dependency on unrelated Work.
7. Per-Work sequencing does not impose global routing order. A blocked handler, execution, wait or retry for A must allow B's independent routing and scheduling to progress. Short serializable storage commits can serialize physically; no global lock may span handler/executor I/O or execution lifetime. Scope capacity can legitimately defer starts, but not unrelated acceptance/routing.
8. An uncorrelated Event can explicitly target existing Work, or a first-match handler can explicitly create fresh Work with stable ID and optional keys. Otherwise it is `unmatched`. Absence of a key never means “use whichever Work is running.” Multiple keys on one Work remain independent external identities with one lifecycle.
9. Terminal Work is immutable. Late Events for its keys get `terminal`, with association and audit intact. Reopen is an extension policy producing a **successor** with a new Work ID and distinct generation-qualified key, e.g. `resource/42/generation/reopen-7`. The adapter must consistently map subsequent deliveries to that generation. A causally linked `core.work.created` Event records predecessor/successor relation as opaque payload; `ParentID` still means child, not predecessor. Old keys stay on the old Work. No reopen policy means no automatic successor. Terminal failed Work follows this rule too.

Bindings are inherited by name with the nearest definition replacing the whole binding; inherited routes resolve against the effective bindings in their target scope. Child Work inherits its parent's scope; an explicitly authorized management create may select another scope. Cross-scope subscriptions need explicit read/alias authorization and do not inherit write authority. Opaque extension config is replaced at its named entry, not recursively merged by core. 01-05 owns the concrete config schema, secret-reference overlays, authorization ceilings, disabling entries and reload snapshots; it must preserve route order and fixed Work scope. A validated config generation is pinned for each decision/attempt; replay uses a committed decision when present, otherwise the current validated generation and records it with the checkpoint.

## Active-event policies and acknowledgements

Policy applies when the selected Work has a running attempt. Waiting Work first evaluates active Waits; ordinary nonmatching Events accumulate as context without bypassing a wait. Ready Work queues eligible input. There is one nonterminal attempt per Work, including pending/parked. Scope concurrency and retry eligibility are checked before Claim; storage Claim itself does not implement those policies.

| Policy | Durable processing acknowledgement | Dispatch/replay and completion |
| --- | --- | --- |
| queue | Event association, ordered pending input and route checkpoint commit together. No immediate second attempt. | Next eligible attempt takes pending input in acceptance order. Preserve consumed-input association/history so replay cannot enqueue it again. |
| inject | Commit an intent tied to Event, target attempt and lease epoch, plus route checkpoint. This is distinct from executor acknowledgement. | Invoke `Inject` outside Tx. Success means accepted for delivery, **not consumed**. Until a stronger 04-02 consumption contract exists, retain input for a subsequent attempt if the target completes; possible repeat presentation is explicit. Recover ambiguous sends using the same Event identity; no exactly-once external delivery claim. |
| interrupt | Commit pending input and interrupt intent with target attempt/epoch before calling `Interrupt`. | Fence the old attempt before any replacement: mark it cancelled/release authority under policy and retain pending input. A cancellation of an attempt for interruption leaves Work ready; cancellation of Work is terminal. Do not overlap process resources until stop/adoption exclusion is established. Replayed control targets the same old attempt, never a new one. |
| drop | Commit `drop` with Event, association, selected route, config generation and reason. | Do not queue, inject or start from this Event. Preserve its envelope and checkpoint for audit; replay is a no-op. Acceptance acknowledgement still follows durable acceptance. |

An active inject/interrupt route must bind to the corresponding mechanically advertised and implemented capability. Reject the binding before scheduling unless an explicit configured `queue` or `drop` fallback exists. Record the fallback reason and effective policy. Unknown policy, `coalesce`, fallback cycles and missing implementations are validation errors. Never infer queue on unsupported control. A runtime failure/ambiguous result from an otherwise supported control is retried with stable intent identity or uses an explicitly configured error fallback; it is not an unsupported-capability shortcut. Post-completion dispatch never targets another attempt using the old intent.

Completion and routing are serialized against Work revision and authority. Before making Work terminal, completion must settle any accepted, unrouted input already resolving to that Work (it can return a retryable conflict until routing finishes). If input routing wins, unconfirmed injection/queued input keeps Work ready after the current attempt completes, then starts N+1. If terminal completion wins before new acceptance, a later Event gets `terminal`; a successor requires the explicit generation policy above. If completion races an in-flight Inject, retain the Event until consumption is proved; a successful return alone cannot erase it. Work may only complete when no pending eligible input remains. 04-02 owns actual delivery/consumption acknowledgements and transport idempotency evidence.

Queue is lossless ordered pending input; it does not replace older Events. Pending-job newest-delivery replacement, timer replacement and detached-busy behavior remain extension requirements for 05-01/05-02. This decision deliberately does not add a coalesce option.

## Wait registration, observation and exactly one wake

A Wait is a durable subscription on its Work's keys, with a type allowlist (empty means any type), exclusive `AfterSequence` and optional one-shot timeout. An Event matches only when its sequence is greater than the boundary, its key is in the Wait, and its type passes the filter. Types/keys are OR within each set and AND between sets. Target Work/authorized alias must agree. Occurrence timestamps and payload conditions are not core predicates. At most one active Wait exists for an attempt; multiple prerequisites are translated by the extension to a suitable Event, not a core condition language.

`AfterSequence` is the execution's acknowledged observation watermark, not the sequence at registration. The caller cannot claim a watermark beyond accepted history. Core scans already accepted matching Events strictly after it **in the registration transaction**, including Events already routed while the attempt was active. Registration joins parking/terminal-wait outcome, lease release, Work waiting, timeout/subscription records and this scan. An immediate match may register and wake in that same transaction; old executor authority is still invalidated. A match at or below the watermark is not reused. For an already-met external condition whose evidence precedes the watermark, the adapter observes/reconciles and emits a fresh canonical observation/alias rather than lowering the boundary or directly waking Work.

For a dependent prerequisite, never attach the prerequisite owner's correlation to the waiting Work. The extension persists an authorized subscription in its namespaced KV containing stable subscription ID, dependent Work/Wait ID, external source key/type translation and last accepted delivery checkpoint. Registration installs it and scans existing observations atomically; a provider read done outside Tx needs post-registration reconcile to close the gap. The adapter translates each matching source Event to an **alias Event** with dependent Work ID, one dependent-owned key, original Event as causation, and stable delivery identity `(subscription ID, original Event ID)`. It accepts the alias and advances its subscription checkpoint atomically. Many dependents can get distinct aliases without sharing ownership. Cross-scope aliases require explicit policy authorization and minimal payload; cancelled/completed subscriptions emit no new runnable activity. State-change/merge/check/job semantics stay in adapters. The reference alias case proves ownership and dedup, not a provider subscription implementation.

Timeout templates are derived from the registration trigger, carry Wait identity and use stable firing identity. Generated timeout/retry Events use normal durable acceptance and causal limits. Timer presence is required **at Wait registration**, not on later historical transitions: a timer may have fired and been deleted before the wake processor runs. The runtime persists enough template/delivery identity to recognize that accepted timeout after deletion. `TimeoutTimerID` remains on history; it is not a live foreign-key requirement after firing.

Wake arbitration is serializable per Wait/Work:

- Select the matching accepted Event with the **lowest acceptance sequence**, including an accepted timeout for this Wait. A timeout already accepted before a normal match wins, even if the normal match occurred earlier externally.
- At `Now == FireAt` the timer is due. If a normal matching Event is already accepted and the timeout is not, that Event wins even at the deadline. Otherwise accept the due timeout and wake from it in one transaction. Real schedulers may accept the due timeout first; the durable sequence then decides. A clock deadline alone never wakes without an accepted Event.
- Atomically change active → woken with winner Event ID, consume/cancel the timeout, remove subscription eligibility and move Work to ready. Mark/enqueue the wake input once. Replaying the winner, a loser, a stale timer fire or wake scan cannot produce a second transition. Preserve Wait history.
- Cancellation first: active → cancelled, delete pending timers/subscriptions, cancel attempts and terminalize Work together. Later matches/timeouts are audit-only. Wake first: retain woken history; subsequent cancellation still fences the pending/resumed attempt and prevents future starts. Neither transition rewrites the other.
- Resume-capable execution stays parked until the scheduler claims the **same attempt** at a higher epoch with a new token. Its original immutable TriggerID remains; pass the winner as the Resume request trigger and record wake linkage separately. Without resume, the waiting attempt is terminal and wake creates **N+1** triggered by that same accepted Event. No direct executor callback, poll result or clock shortcut bypasses Event acceptance.

## Lease recovery, retry and cancellation

Lease expiry is exclusive; `Now == ExpiresAt` has lost authority. Expiry/release makes the same running attempt recoverable, not permission to launch another attempt. Recovery claims that attempt with a higher epoch, persists recovery-in-progress authority and invokes `Recover` outside Tx using opaque executor metadata. Competing recoverers cannot both hold a live epoch. A live lease cannot be stolen. Parked wait continuation uses Resume and is distinct from detached adoption.

Adoption succeeds only when the executor verifies the existing process/finished handle and replaces old credentials before allowing mutations. It never calls Run. A finished detached result is committed under the recovered lease. Unknown/dead/unverifiable metadata returns `ErrNotAdoptable`; core records the interrupted attempt as failed under the new fence, then applies retry policy. “Unverifiable” does not establish that a process stopped: resource/process exclusion or confirmed termination remains necessary before replacement launch. Recovery crash repeats recovery of the same attempt after expiry, with another epoch. Stale results, tool calls, emissions and heartbeat renewals fail even if owner names or process IDs are reused.

Failure atomically ends the attempt, leaves Work ready, records eligibility and arms the retry Timer. The parity default uses **three total failure attempts** (matching source `MaxAttempts=3`), waits 5 minutes after failure 1 and 10 after failure 2, then stops automatic retries while retaining nonterminal Work. With an explicitly configured four-attempt budget, failure 3 waits 15 minutes; the suite uses that budget to exercise all three backoffs. No jitter in this reference policy. The failure count is policy state, separate from monotonic Execution.Attempt. A successful continuation or explicit manual retry resets the automatic failure budget by configured policy; attempt numbering never resets. Executor rate-limit classification can select a generic retry-after hint (source parity: known reset + 2m, otherwise 30m) without adding provider fields/branches to core. Repeated policy failures must stay bounded; 02-04 implements hint validation and executor fixtures.

Backoff expiry emits `core.retry.due` with failed trigger ancestry; it does not Claim directly. Routing the accepted event makes Work eligible only if its failed-attempt generation is current, Work remains nonterminal and no live attempt/wait blocks it. Events queued during backoff do not implicitly clear eligibility. A manual accepted `core.retry.requested` Event can clear backoff/exhaustion, cancel the old timer and request the next attempt. Duplicate/stale retry Events cannot clear a later failure's backoff. Claim is still subject to scope capacity and executor binding/resource checks. An explicit terminal-on-exhaustion policy can fail Work; subsequent retry needs a successor.

Cancellation commits cancellation of active/pending/parked attempts, Waits, timers and queue eligibility before terminalizing Work. Tokens lose authority at that commit. Interrupt/cleanup happens afterward and cannot restore authority. Retry first then cancel: accepted due Event survives as history, eligibility/attempt are removed or cancelled. Cancel first then retry: due processing cannot rearm or Claim. Recovery/adoption first then cancel: the new epoch is fenced too. Completion first then cancel: preserve the completed terminal record; cancellation never rewrites terminal Work. These orders use trusted transaction admission time and revisions, not process message timing.

## Causal bounds and rejection evidence

Only trusted external ingress/configured independent schedule/operator activity creates roots. Executors, route-derived activity, extension operations, subscription aliases, child creation and executor-generated timers **must** have trusted causal ancestry. Core derives the immediate parent from the accepted trigger/authority; clients cannot select a root, sever ancestry through a child, invent a missing parent or emit a privileged core family. Child creation and its `core.work.created` Event are atomic. An executor-created timer inherits its arming trigger even if it fires days later. An independent configured recurring schedule may create root occurrences; an execution-created recurrence stays on its original chain. Recovery/resume retains the root rather than resetting it.

Defaults: root depth 0, maximum derived depth **32**; at most **128 new derived Events per root per fixed UTC minute** (`floor(trusted Unix seconds / 60)`). At the cap the next new Event is rejected; the next minute restores rate capacity but never resets depth. Siblings, aliases to other scopes, child Work, builtins and timers share the root's budget. The fixed window permits up to twice the minute allowance across a boundary; it is deliberately not a rolling-window promise. 01-05 validates positive bounded configuration; a child cannot raise the root's pinned limits.

Deduplication precedes budget charging. Counters, accepted Event and associated child/route/timer-fire effects commit atomically; rejected effects all roll back. Persist root/depth and bucket counts or reconstruct from retained ancestry; memory-only counters fail restart. Compaction must preserve enough ancestry/counters to enforce pinned limits. Check limits at **every derived acceptance**, including FireTimer, not only the toolbelt emit operation. Arming a future timer need not spend a token before it fires, but cannot discard ancestry. Over-limit timer firing records rejection and disables that firing; no tight retry loop and no wake without an Event. Control-plane cancellation/lease fencing must still operate without needing another derived-event token.

Rejected derived input gets a durable, redacted diagnostic keyed by attempted delivery/parent, with reason, root/depth/budget and relevant Work/Execution/trace, without payload/secrets. It is not another recursively routed Event and consumes no chain token. Execution-facing calls fail explicitly; timers/routes stop the rejected branch. Independent roots continue. A crash between refusal and diagnostic must be recoverable through the durable originating intent/timer; 02-03/02-08 own production audit persistence/export. The reference stores safe rejection identity/reason in KV and demonstrates bounded acceptance; it does not claim crash-safe diagnostic delivery.
