# Durable routing and Work lifecycle

Ticket 02-03 implements the routing, Work lifecycle and causal limits from [B04](runtime-semantics.md). The [runtime](../../internal/runtime) uses public storage and extension contracts; [integration tests](../../integration/routing_test.go) compose it with real SQLite. A host still needs the scheduler, timer driver and authenticated management service delivered by subsequent tickets.

`NewRouter(store, now, RouterOptions)` takes a trusted clock, a configuration generation, deterministic route handlers and registered executor implementations/fallbacks. `RouterOptions.Bindings` is keyed by executor registration, while routes refer to effective Scope binding names. The router checks implementations with `extension.ValidateBinding`; capability flags alone cannot establish control support. Queue-only fixtures may omit an executor, but cannot claim optional capabilities. Router option maps are copied at construction. Stored Scope routes resolve root to leaf, preserving override slots, and inherited routes use the target Scope's effective named bindings. Configuration loading, authorization ceilings and reload publication remain 02-06.

`Route(ctx, eventID)` reads durable accepted input and evaluates handlers outside storage transactions. Each handler receives a detached snapshot. The first match wins, including an effective drop; handler errors stop processing. The commit revalidates Scope and Work snapshots, correlation ownership and input order. A changed snapshot requires reevaluation. Conflicting identities leave the Event unrouted for diagnosis. A blocked handler holds no global coordination lock, so independent Work can progress.

Work scope and owned correlations stay fixed. Attachment adds keys atomically with route effects and processing checkpoints. Earlier accepted, still-unrouted input for newly attached keys joins the same Work in acceptance order; previously checkpointed unmatched/drop/terminal input stays historical. Already owned keys cannot transfer between Work records. Explicit Work, Execution and correlation targets must agree.

The route transaction persists a `RouteRecord` with Event/Work, selected route/binding, generation, effective policy and reason alongside `MarkRouted`. Queue input retains acceptance order. Active inject/interrupt policies persist stable intents targeting the specific attempt and lease epoch, while retaining input for later presentation until consumption is proved. The router makes no execution or control calls. Unsupported controls require an explicit queue/drop fallback; a route selecting a different binding from the active attempt also requires an explicit fallback. Ready or waiting Work queues ordinary matching input instead of applying running-attempt controls. The scheduler must pin attempt configuration and validate dispatch against that generation, including changes to an executor behind the same binding name.

`PendingInputsInTx` and `ConsumeInputsInTx` let a scheduler join selection, claim and consumed-input history in one guarded transaction. `PendingInputs`, `Decision` and `Intents` inspect durable coordination records. Consumption removes pending entries but preserves their attempt association; replaying a route cannot enqueue them again. These are trusted internal APIs, not an execution-facing claim or acknowledgement protocol.

`Complete` requires current attempt authority and refuses to overtake accepted, unrouted input belonging to that Work. Remaining queued or unconfirmed injected input leaves Work ready; otherwise it becomes completed. `Cancel` atomically cancels active attempts and Waits, removes owned timers and queue eligibility, and terminalizes Work. Physical process cleanup follows that commit in the scheduler. Cancellation needs no derived-event token. Terminal records remain immutable and late input is checkpointed as terminal.

`CreateChild` selects parent Work, Scope and trigger from the leased attempt. `CreateSuccessor` is a trusted policy operation requiring terminal predecessor ownership and distinct external keys. Each publishes a new Work and a causally linked `core.work.created` Event atomically. The creation payload records the child or predecessor link; a successor has no child `ParentID`, and old keys stay with the predecessor. The extension supplies a consistent generation-qualified identity for subsequent external deliveries.

`NewCausal(store, now, limits)` coordinates derived acceptance. `Derive` and the transaction-level helpers require a parent chosen by trusted core code. `Emit` selects it from the fenced attempt's immutable trigger and rejects a supplied conflicting parent, reserved core families and cross-Work identity. Authentication, event declarations and operation authorization belong to the management/toolbelt boundary in 02-06. Existing `Ingress.Accept`/`AcceptInTx` remain trusted acceptance primitives whose callers must enforce this distinction; registered ingress adapters can supply only external roots.

Defaults are depth 32 and 128 new derived Events per root per fixed UTC minute. Root depth is zero; deduplication spends no token. Root limits are pinned durably on first derived acceptance, and siblings/children retain those limits across runtime recreation and configuration changes. Event ancestry, bucket increments and associated effects commit together. Missing parents, depth excess and rate excess produce durable redacted diagnostics without accepting another Event or consuming a token. The next minute restores only rate capacity. Future timer firing must use the same derived boundary rather than raw storage acceptance; 02-05 owns its due-event and rejection handling.

The current implementation inspects accepted history and coordination KV for routing and duplicate resolution. It establishes correctness, not a high-volume throughput or retention guarantee. Retention must preserve causal metadata and deduplication evidence. OpenTelemetry export and operator history presentation remain 02-08; real executor delivery/consumption semantics remain 02-04/04-02.

The SQLite integration adapter runs nine applicable shared runtime cases over persistent connections and independently reopened handles. Its `Start` method only installs an execution fixture through public storage operations; it does not implement a scheduler or claim production dispatch coverage. Direct regressions cover attachment backlog and nonresurrection, blocked handlers and cross-key ordering, detached snapshots, ancestor revisions, execution-only targets, effective binding overrides, intent identity/fallback, cancellation, conflicting input isolation and successor target Scope. Separate causal and linked-Work tests cover restart-pinned limits, concurrent sibling quotas, replay, forged ancestry, stale leases and atomic child/successor publication. Full wait/retry/recovery cases remain assigned to their implementation tickets.
