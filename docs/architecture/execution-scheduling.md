# Execution scheduling, recovery and control

Ticket 02-04 implements [B04 execution policy](runtime-semantics.md) over the public storage and executor contracts. [The scheduler](../../internal/runtime/scheduler.go), [retry policy](../../internal/runtime/scheduler_policy.go) and [control dispatch](../../internal/runtime/scheduler_control.go) compose with the production router. They contain no process, service, SQLite or configuration-loader dependency. A host drives these operations; the daemon, authenticated toolbelt, durable timer driver and shell process implementation remain subsequent tickets.

`NewScheduler(store, now, router, options)` takes a trusted clock, owner, configuration generation and mechanically validated executor registrations. Defaults are four concurrent attempts, a one-minute lease, a one-hour execution timeout and three total failure attempts. Scope limits apply to the selected scope and its ancestors. Constructor options are copied. Binding inheritance resolves before claim; the commit rechecks Work, input and Scope snapshots.

`Start` atomically selects ordered pending input, creates the next monotonic attempt, claims its lease, pins behavior and records consumed-input history. The durable launch intent precedes `Run`. Executor calls, capability methods and retry-hint callbacks run outside coordination transactions; a blocked executor cannot retain the storage lock. No process-local global lock coordinates claims. Real serializable storage prevents competing schedulers from creating simultaneous attempts or exceeding configured capacity.

The attempt snapshot retains its configuration generation, full binding, executor registration, capabilities, retry policy, timeout deadline, control error fallback and handoff policy. `HistoricalExecutors[generation][registration]` must reinstall the exact older implementation for recovery/control after reload. A missing generation is unsupported; it never selects a replacement executor silently. Future attempts use current validated bindings and policy. Secret resolution and authorization ceilings remain the 02-06 composition boundary; secrets are not part of durable attempt snapshots.

`Start` and `Recover` return an `Attempt` containing its lease, request and handle. An executor must successfully use the fenced `PersistRecovery` callback before returning a successful handle. The scheduler validates bounded opaque JSON recovery metadata and checks current authority around launch acknowledgement. Missing acknowledgement or an ambiguous operation records a safe failure and retains resource exclusion. Executors still own closing the process launch/persist crash window through deterministic discovery, prelaunch intent or cleanup, as required by B03.

`Recover` claims the same nonterminal attempt at a higher epoch and persists recovery-in-progress before calling `Recover` outside storage. It never calls `Run` to replace that attempt. Renew/release use the exact lease; release makes that same attempt recoverable. Old outcomes, metadata callbacks and renewals fail after expiry, release, cancellation or a newer epoch. Observation cancellation cancels `Wait` observation only and does not assert that a detached process stopped.

Lease fencing and physical resource exclusion are separate. Durable attempt holds survive restart, including terminal attempts with uncertain external processes, and count against Work/global/ancestor capacity. `ErrNotAdoptable`, transport errors, timeout and a successful interrupt request do not prove that resources stopped. Replacement remains blocked until the trusted host supplies `ConfirmStopped(executionID, expectedEpoch)`. A successfully observed structured terminal result establishes finished attempt resources. Confirmations cannot target an attempt that has since been adopted at another epoch. Real shell cleanup, adoption and resource evidence belong to 02-07/02-09; the generic scheduler does not inspect process IDs or executor metadata. 02-07: the [shell executor](shell-executor.md) supplies verified-stop evidence through `Stop(execution, epoch)` before the host calls `ConfirmStopped`. 02-09: the [daemon](daemon-core-gate.md) renews observed leases and performs that stop/confirm after lost authority, observation failure or a failed recovery; `Recover` carries an unapplied toolbelt declaration to the new epoch.

`Observe` waits outside storage, then applies a lease-fenced structured result. Completed Work cannot overtake accepted unrouted input; queued or unconfirmed injected input leaves it ready for N+1. Results preserve common outcome, usage and artifact-reference history. Failed attempts return Work to ready with bounded retry eligibility, unless an explicit terminal-on-exhaustion policy fails Work. `Timeout` requires the persisted deadline to be due and current lease authority, then records failure and retains the uncertain resource hold. A host must recover expired authority before applying such a mutation; a clock deadline does not grant a stale lease authority.

Handoff ends the attempt and leaves Work ready for eligible input. Automatic continuation is off by default. If explicitly enabled, a stable derived `core.execution.handoff` Event and queue checkpoint join the outcome transaction. Causal refusal records a diagnostic and stops that continuation branch while preserving the handoff outcome. A bare waiting outcome cannot bypass event-based suspension; [02-05](timers-waits.md) supplies predicate registration, structured waiting results and fenced acknowledgement.

Failures arm a durable retry Timer template with the failed attempt generation and trigger ancestry. Default delays are five and ten minutes; an explicit four-attempt policy adds fifteen minutes. Failure counts are separate from attempt numbers. Up to 100 configured delays yield 101 total attempts, matching the B05 schema. Generic retry hints select reset time plus two minutes, or thirty minutes for an unknown reset; invalid/past/excessive hints fail explicitly. Hinted failures still consume the bounded failure budget. Provider classification stays outside core.

Executor errors implement the optional public `extension.RetryHintProvider`; they do not import runtime implementation types. `Complete`/`Fail` accept a trusted host's finished structured result. Future toolbelt outcome declarations must still establish process/resource exclusion before granting replacement capacity; a client declaration alone is not stop evidence.

`ProcessRetry` consumes an already accepted trusted retry Event. The timer driver must first accept through `AcceptDerivedInTx` and atomically remove/fire the timer. A due clock alone never clears eligibility. `core.retry.requested` (B04) and `core.manual.retry` (B05) are manual aliases. The event must follow the current failure's acceptance-sequence boundary, and a processed Event cannot clear a later failure. Manual retry resets the automatic failure budget, not attempt numbering. Old due generations, terminal Work and replay remain historical; live attempts/Waits prevent retry. Ordinary queued input during backoff does not clear it.

`DispatchControl` claims a durable intent, performs `Inject`/`Interrupt` outside storage, and acknowledges only with the same live dispatch token. It uses the pinned attempt executor, capabilities, target and epoch. A new executor registration cannot grant control capability to an older attempt. Inject acknowledgement means accepted, not consumed: pending input remains eligible for subsequent presentation. Ambiguous delivery retries the same intent/Event identity, with no exactly-once transport promise. An explicit pinned queue/drop error fallback is recorded; provider error text is not persisted. Late acknowledgements, completed targets and superseded epochs cannot retarget a newer attempt.

Interrupt fences the old attempt and leaves Work ready before sending control, but retains its resource hold until stopping is verified. Work cancellation atomically fences attempts, Waits, owned timers and queue eligibility through the router. Physical cleanup follows that commit. The host must not treat acknowledgement of a stop request as proof of resource exclusion.

[SQLite scheduler tests](../../integration/scheduler_test.go) run eleven applicable shared runtime cases through the production scheduler with persistent and independently reopened handles. A small explicit timer-contract adapter accepts the retry Event and fires its stored timer for these tests; the production due-event driver remains 02-05. Additional cases cover blocked Run progress, global/scope/ancestor capacity, same-attempt recovery, stale callbacks, uncertain-launch restart, resource holds, cancellation orders, inject/completion races, interruption, deadlines and handoff. [Policy regressions](../../integration/policy_test.go) cover generation-pinned retry/capabilities, missing launch acknowledgement, retry bounds and explicit control error policies. No real process, daemon crash drill, service integration or hosted CI execution is claimed here.
