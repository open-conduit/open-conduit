The toolbelt is how a running execution asks Open Conduit for outcomes, and the local management API is how an operator controls the daemon. Together they implement [B03](../extensions/) toolbelt authority and [B05](../config-management/) configuration, secrets and the local management API. The pieces are the runtime [toolbelt](https://github.com/open-conduit/open-conduit/blob/main/internal/runtime/toolbelt.go) and [operator control](https://github.com/open-conduit/open-conduit/blob/main/internal/runtime/manual.go) operations, [configuration loading/validation/secrets](https://github.com/open-conduit/open-conduit/tree/main/internal/config), the [management server](https://github.com/open-conduit/open-conduit/tree/main/internal/management), the public [client](https://github.com/open-conduit/open-conduit/blob/main/client/client.go) and the [`open-conduit` operator commands](https://github.com/open-conduit/open-conduit/blob/main/internal/cli/operator.go). The daemon composes them with the scheduler and poll loops and owns the server's lifetime ([daemon composition](../daemon-core-gate/)); the shell executor builds the execution environment and the `os` CLI transport ([shell executor](../shell-executor/)).

## Toolbelt authority

`runtime.Toolbelt` implements `extension.Toolbelt`, `TokenIssuer` and `Registrar`. Tokens are unpadded base64url encodings of 32 random bytes. Coordination storage keeps only their SHA-256 digest, the pinned authority, binding and generation, a revocation ID and revocation state. Plaintext is returned once to the trusted issuer. With `SchedulerOptions.Toolbelt` set, the scheduler issues a fresh token after every claim, recovery and resume, for executors whose transport is not `none`. It places the token in `RunRequest.Context`, with the execution's own endpoint (see [Execution endpoints](#execution-endpoints)). Issuing a token revokes all lower-epoch tokens for that execution. Token lifetime is limited by the attempt deadline (or an optional `Lifetime`), so it can never outlive active authority. The same sweep deletes a token record, with its ID and per-execution index rows, 24 hours after it was revoked or expired; a deleted token is unknown, which every check refuses just as it refused the revoked one.

Every call, reads included, passes these checks in order:

1. Digest lookup, revocation and exclusive expiry.
2. Narrowing `scope_id`/`work_id`/`execution_id` assertions.
3. The operation is declared and in the token allowlist.
   An operation that serves a capability (`Operation.Serves`) is served only to the host's own call for it (`ToolCall.Capability`, which only the host sets, for [git's transport](#git-transport)): any other call of it is `422 capability_only` with what to do instead, and so is any `POST /v1/toolbelt/call` that names a `capability` at all, as the request carries none ([extensions](../extensions/)). Its answer is never kept for replay.
4. The current B05 ceiling, checked through `ToolbeltOptions.Authorize` outside storage. A config reload or disabled scope therefore revokes immediately.
5. Under the lease guard in the call's transaction: the execution is running at the token's epoch, the owner matches, the lease is not expired, the Work is running in the token scope and the segment has no pending declaration. A genuine token whose segment has declared a wait or outcome is refused with `extension.ErrAuthorityReleased` (`403 authority_released`, recorded as `toolbelt.result` `authority_released`), which wraps `ErrUnauthorized`. A call that has not run, refused because its lease lapsed under it (a host that slept or stalled past the lease) or because recovery has already superseded its token, while its execution is still running and its Work open, is refused with `extension.ErrAuthorityRecovering` (`503 authority_recovering`, recorded as `toolbelt.result` `authority_recovering` with its `toolbelt.refusal`), which also wraps `ErrUnauthorized`: recovery adopts the same process with a fresh token, so the same call made again with the execution's current credential is accepted. The toolbelt's reads (guidance, and the operations serving a capability) refuse a token recovery superseded the same way. The `os` toolbelt CLI, its MCP server and its git remote helper (`os git-remote`) do that themselves, for calls and reads alike: they re-read the token file, which recovery replaces, and make the call again with the same request ID, backing off for up to 30 seconds, so the agent sees only the answer. A refusal after an extension handler has started (its effect may have happened), a token past its expiry under a live lease and a token whose execution has finished keep the bare refusal (`TestProductionToolbeltRecoveringOnlyWhileAdoptable`). Every other failure is the bare `403 forbidden`, so an executor can tell "I already parked this run" and "retry shortly" apart from a bad, forged or superseded token.
6. For an extension operation, after the replay lookup: every registered gate but the operation owner's (see [Gates](#gates)).

Emit uses only declared and allowed families. It assigns trusted execution source, Work, Execution and continuation causation, rejects forged sources/parents/targets and unowned correlations, and accepts through `AcceptDerivedInTx`, which applies causal bounds. The daemon passes the configured `causal_max_depth`/`causal_per_minute` to the toolbelt, so an execution's first emission off a new root pins the configured limits. `create_work` joins child creation and its causal `core.work.created` in one transaction, and is refused for a kind the token's `WorkKinds` or the current config's `work_kinds` doesn't grant ([child Work](../routing-lifecycle/#child-work)). `cancel_work` cancels only the calling Work's own child that hasn't ended, recording the cancel on the child in the transaction that cancels it. The host adds its own guidance to the operations': the kinds the token may ask for, each with the description of the `work` route that takes it, and how to wait for the answer (and, when the grant includes `cancel_work`, how to cancel a child it no longer needs); and, for child Work a parent asked for, that its turn's `result` is what the parent receives. Extension handlers run outside storage after a fenced authority check. They receive validated authority and never the token. Handler refusals (`extension.OperationError`) return `422` with the handler's code and message.

Idempotency semantics:

- **emit**: idempotent by delivery identity.
- **Request IDs** (`request_id`, or the HTTP `Idempotency-Key` when absent): replay the committed result for the same execution and operation, and reject a changed body with `ErrRequestConflict`. Replay records name their execution. The retention pass (`Toolbelt.SweepToolbelt`) deletes them 24 hours after they were written once their execution has finished, since only that execution's tokens could replay them and those are revoked when it finishes. Records written before they named their execution are kept.
- **Children**: allocate stable IDs from the request ID before commit.
- **Extension handlers**: run once per request ID, unless the host crashes in the window between the handler's effect and the commit of its result: the retry then runs the handler again. Handlers must be idempotent on the request ID ([extension protocol](../extension-protocol/#operation-handlers-and-request-ids)). `TestProductionToolbeltReplayWindow` drills that window.
- **wait and declare_outcome**: release authority, so a duplicate after a lost response fails authorization with `authority_released`, which says the declaration landed. Resolve anything further by inspection, as B05 requires.

`wait` and `declare_outcome` are recorded under the fence as a per-epoch declaration. Toolbelt authority is released at once. A request alone does not register a predicate or establish physical exclusion; this resolves the B03 "atomic release" wording against the scheduler's handshake rule ([execution scheduling](../execution-scheduling/), [timers and waits](../timers-waits/)). When the trusted host observes the segment finish or suspend, `Scheduler.Complete` applies the declaration:

- **Declared wait**: arms its timeout timer and registers the Wait in one transaction (via `WaitWithResult`), keeping executor usage/artifacts. Resume-capable executors park; other executors end waiting.
- **Declared outcome**: replaces the executor's structured outcome.

The declared watermark defaults to the attempt's acknowledged input, so registration backscans every Event accepted in between. A type-only `wait` subscribes on the Work's keys, and an unapplied declaration survives recovery ([daemon composition](../daemon-core-gate/)). Transport/observation errors still follow failure policy.

### Gates

A registration may carry a gate (`extension.Registration.Gate`). An installed package declares `provides.operation_gate`, serves `operation.gate` and needs the `operation.gate` permission, which the operator sees at install; without it the host installs no gate, and with it the package is asked only about calls in the scopes it is configured for. The toolbelt asks every gate, in registration-name order, before it runs another registration's operation; a gate never sees its own registration's operations, and builtins (`emit`, `create_work`, `cancel_work`, `wait`, `declare_outcome`, `read_context`) pass no gate. A gate answers in one of three ways:

- **Let the call through**: the next gate is asked, and once all have, the operation runs.
- **Park the caller**: it returns a `WaitPlan`, which the toolbelt declares exactly like a translated wait, owned by the gating registration (so its dependencies use that registration's dependency filter). The operation does not run, authority is released, and the call returns the plan's output and the Wait. The caller is resumed by whatever the plan waits on, or its timeout, and makes the call again.
- **Refuse**: its error reaches the caller verbatim (an `extension.OperationError` is `422` with its code and message), wrapped in `extension.GateRefusal`, which names the gate. Authority is kept for other calls.

A gate that panics, or an installed one that times out, crashes or answers with anything but an operation error, refuses with `gate_failed`: the host fails closed. A parked call records `toolbelt.called` with `toolbelt.gate` naming the gate; a refused one records `toolbelt.rejected` with `toolbelt.result` `gate_refused` and the same attribute. The core knows nothing of why a gate decides as it does. The `human` extension's approval gates are the first ([human decisions](../../workflows/human-decisions/#approval-gates)). A registration can also carry a start gate (`extension.Registration.StartGate`), which the scheduler, not the toolbelt, asks before a Work's first attempt starts ([start gates](../execution-scheduling/#start-gates)).

### Execution endpoints

`SchedulerOptions.ToolbeltEndpoints` is required whenever `SchedulerOptions.Toolbelt` is set (`NewScheduler` refuses the options otherwise), so each execution that uses the toolbelt gets its own toolbelt endpoint in a host-owned run directory, `<state>/runs/<key>/`, where the key is 16 hex characters of the execution ID's SHA-256 ([`management.Endpoints`](https://github.com/open-conduit/open-conduit/blob/main/internal/management/endpoints.go)):

- `toolbelt.sock`, owner-only `0600`, served by `Server.ExecutionHandler`. It answers only `POST /v1/toolbelt/call`, `GET /v1/toolbelt/guidance` (the agent guidance of the token's granted operations, and each one's summary and input, which `os mcp` serves as its instructions) and `GET /v1/toolbelt/serving?capability=` (which of the token's granted operations serve a capability; nothing in a run uses it now) and the git routes: `POST /v1/toolbelt/git` (open a session for a repository), `DELETE /v1/toolbelt/git/{session}`, and `GET` and `POST /v1/toolbelt/git/{session}/{service}` ([git transport](#git-transport)). Every other path is `404 not_found` before authentication, so operator endpoints are not served there to either credential class. An operator credential on the toolbelt call is `403 wrong_credential_class`, as an execution credential is on the management socket. Each request asserts the socket's execution (as `execution_id` would), so a token issued to any other execution fails the toolbelt's narrowing check (`403`), as does a call that asserts another execution.
- `token/token`, the execution's current token. After every claim, recovery and resume the scheduler issues the fresh token and calls `ToolbeltEndpoints` before the executor's `Run`, `Recover` or `Resume`. It writes the token through a temporary file in `token/` and a rename, so a process that sees `token/` through a directory mount sees the rotated file (a single-file bind mount pins the old inode). The executor receives the endpoint as `ExecutionContext.ToolbeltEndpoint` and the file as `ToolbeltTokenFile`, and points its process at both (`OS_ENDPOINT`, `OS_TOKEN_FILE`) instead of writing a token file of its own.
- `execution`, the execution ID, so a restarted daemon can tell whose run directory it is. A run directory that names another execution is refused.

With the endpoint the scheduler also gives the executor `ExecutionContext.ToolbeltDir` (`SchedulerOptions.ToolbeltDir`: the directory holding the host's `os` binary), so an executor that runs outside the host's own directory, such as an installed package, can name `os` and `os mcp` without guessing where it lives. Every attempt, with a toolbelt or not, gets `ExecutionContext.PlaybookDir` (`SchedulerOptions.PlaybookDir`: the directory the daemon writes the playbooks to, one per skill as `skills/<name>/SKILL.md`), so such an executor can start a turn on the playbook its binding names. Both cross the [extension protocol](../extension-protocol/) as `toolbelt_dir` and `playbook_dir` in the run request's context.

The token, the lease epoch and the binding's allowed operations are checked on every call. The daemon's loop closes the socket and removes the run directory of every execution that is gone, or terminal with its process confirmed stopped (`Scheduler.Holding`), including run directories an earlier daemon left. A parked execution keeps its run directory. So does one that timed out or was cancelled, until the host confirms its process stopped: its token is revoked when it ends, so a call the process makes in the meantime reaches the host and is refused there (`403`, recorded as `toolbelt.rejected`), rather than failing in the process for want of a token file. If the token file is gone anyway, `os` says the execution has ended instead of that the toolbelt was never set up. On shutdown the daemon stops serving every socket and keeps the run directories; the next daemon serves a socket again when it adopts that attempt (recovery calls `ToolbeltEndpoints` with the rotated token).

A Unix socket path is limited to 104 bytes on macOS. When `<state>/runs/<key>/toolbelt.sock` would pass 100 bytes, the socket goes in `/tmp/open-conduit-<uid>/<key>/toolbelt.sock` instead, both directories owner-only and refused if they are not; the token stays in the run directory. If that path is too long as well, the attempt fails with `toolbelt endpoint unavailable` and the error names the path and asks for a shorter state directory.

The management socket is operator-only. An execution token is `403 wrong_credential_class` on every route there, `/v1/toolbelt/call` included, so it is served only by its execution's own `toolbelt.sock`. Executors that call the toolbelt themselves (the GitHub hold executor) dial the endpoint in their `RunRequest` like any other, which is that socket. Test harnesses that call the toolbelt in process pass a `ToolbeltEndpoints` of their own. Earlier releases also served execution tokens there, so that an attempt launched by a daemon from before per-execution sockets (v1.8.0) kept its toolbelt when a newer daemon adopted it. An attempt still running from such a daemon loses its toolbelt on upgrade.

### Git transport

The run's git never holds a credential. The host signs git's requests in itself, over the execution's own toolbelt socket, so it works the same for the host, a process sandbox and a container.

- **The layer.** `extension.GitTransportLayer(hosts...)` is a run environment layer that sets, through `GIT_CONFIG_*`, `url.open-conduit::https://<host>/.insteadOf https://<host>/`, `alias.remote-open-conduit=!os git-remote` and `protocol.open-conduit.allow=always`. Git then runs `os git-remote <remote> <url>` as the remote helper for that host's `https` remotes. There is no second binary: git's alias runs `os`.
- **A session.** `os git-remote` asks `POST /v1/toolbelt/git` with `{"url"}`. The host asks each operation the execution is granted that serves `git.credential`, in turn, with `{protocol: https, host, path}`, until one answers with a username and password. That call is the host's own (`ToolCall.Capability`, set only by the host), and gates apply to it as to any call, so one approval opens one session, which serves one git command. The host keeps the credential in memory in the session (one transport per daemon, so a config reload keeps it and a restart doesn't), until the credential's expiry or an hour, whichever is first, or until the helper ends it with `DELETE /v1/toolbelt/git/{session}`. It returns only an opaque session ID.
- **The exchange.** The helper speaks git's `connect` remote-helper protocol. It fetches with git protocol v2 (each request is one exchange) and pushes with receive-pack's one exchange, relaying through `GET /v1/toolbelt/git/{session}/{service}` (the advertisement, `info/refs`) and `POST /v1/toolbelt/git/{session}/{service}` (an exchange, streamed). `service` is `git-upload-pack` or `git-receive-pack`, nothing else. The host forwards to `https://<host>/<path>/info/refs?service=...` or `/<service>` with Basic auth and never follows a redirect. On every request it checks that the execution's token is live and still granted an operation that serves `git.credential`.
- **No credential, no session.** When no granted operation gives a credential for the repository, the host refuses the session (`git_no_credential`) and `os git-remote` hands the command to git's own `git remote-https`, which reaches the repository directly and unsigned, as git would without the transport. The host forwards nothing it can't sign in, so it is not a proxy and doesn't widen the sandbox's network.
- **A held gate.** A gate holding the sign-in refuses the session with `git_sign_in_held` and the gate's instruction. The helper prints `os: no git sign-in yet: <instruction>`, which git shows the agent.
- **The boundary.** No request from the run gets a capability's answer: the toolbelt call refuses any request that names a `capability` (`capability_only`), and an agent's own call of an operation that serves one is refused the same way. This is an authority boundary, put at the host. `os git-credential get`, `store` and `erase` are retired: they answer nothing and ask nothing, and stay so an old config naming the helper keeps working.

### Registered operations

The daemon registers each extension's operations on every generation's toolbelt and lists them in the config registry (`Registry.Operations`), so a binding may grant them:

- GitHub tool operations, with translated wait operations declared like `wait` ([engineering tools, waits and playbooks](../engineering-tools/)).
- Slack operations (`slack.context`, `slack.thread`, `slack.reply`) as a second extension registration ([Slack extension](../slack-extension/)).
- Introspection operations, only for a generation with an enabled `introspection` entry.

**Operation names.** Each extension owns the namespace of its registration name: every operation it registers is `<name>.<suffix>`, so `github.*` belongs to the `github` registration alone. A registration name is a lower-case letter followed by lower-case letters, digits, `-` or `_` (`extension.RegistrationName`, the same rule as a package manifest's name), with no dot, so two namespaces never nest. `Toolbelt.Register` checks `extension.OwnsOperation` and refuses an operation outside the registration's namespace with `invalid` whatever order extensions load in, so a package that starts first can't take the calls meant for another. A collision (a repeated registration name, a builtin such as `emit`, or an operation registered twice) is refused with `conflict`. Either error names the operation and why, and a refused registration registers nothing. An installed package's operations are also checked against its manifest name when it is discovered and installed, and its names can't be ones the host itself takes or another package claims. The shared `operation_namespace` toolbelt case checks the rule on every toolbelt implementation, with a negative control that accepts squatting.

Translated emissions (`Operation.Emit`) are accepted under the same fence, replay and causal checks as `emit` ([issue reporting](../issue-reporting/)). A registration can seal some of its families (`Registration.SealedEventTypes`, `"sealed": true` on a manifest family): the builtin `emit` refuses a sealed family as `unauthorized` although every execution's authority lists the registered families, so only the registration's own Emit operations, which check their input at the host, emit it. A route can then trust such an Event: the Slack extension seals `slack.thread.opened`, which attaches a thread to the Work that posted it, so no executor can claim a thread with the builtin `emit`. The `sealed_family` toolbelt case checks it, with a registrar that drops the seal as its negative control. The daemon narrows each binding's grant to the operations registered on the generation's toolbelt, so a binding that still lists the operations of a disabled extension keeps running (its calls are `undeclared`) instead of failing token issuance.

### Toolsets

A grant names operations, but an extension's agents need them by role: an issue's author, a PR's reviewer. A list of names copied into the config when setup ran never receives an operation a later release gives that role, so the agent is refused something the operator never meant to withhold (issue #461). An extension therefore publishes **toolsets**, named sets of its operations for each role, and config grants one by name.

- **Granting.** An entry of a scope's `authorization.operations`, a binding's `operations` or a binding grant's `operations` is an operation name, a toolset as `@<name>` (`@github.author`), or either denied with a leading `!` (`!github.pr.edit`, `!@github.reviewer`). `config.ResolveOperations` turns a list into operation names: what it names and its toolsets' operations, in order, less what it denies. Explicit names and toolsets mix freely, so an operator can still narrow or widen a grant one operation at a time.
- **Resolved where the host checks.** Validation resolves every list against the running release's registry, so a snapshot's `EffectiveScope` holds only operation names and `AuthorizeOperation`, the token grant and the ceiling check are unchanged. The stored generation keeps what the operator wrote (`@github.author`), and the daemon revalidates it at every start, so an upgrade that adds an operation to a toolset grants it to every install that names the toolset, with no config change and the same config hash. Running attempts keep their pinned grant; the next attempt gets the new operation.
- **Failing closed.** A toolset, operation or denial that isn't registered is `unknown_reference`, so a typo never grants, nor fails to deny. A toolset grants only registered operations, and only within the ceiling: a binding's toolset is narrowed to what its scope grants, and a child scope's to its parent's, rather than refused. A release that adds an operation to a toolset therefore never stops a config whose scope lists operations by name from loading; doctor reports what the narrowing leaves out (below). An explicit name outside the ceiling is still `authority_widening` or `operation_denied`.
- **Publishing.** A package declares `provides.toolsets` in its manifest ([manifest](../extension-protocol/#manifest)), which `inprocsdk` fills from `inproc.Toolsetter` for an extension written on `extension/inproc`, so first-party and installed extensions publish them the same way and the core resolves them without knowing what any of them is for. A toolset (`extension.Toolset`) is named in its extension's namespace (`github.author`), grants only that extension's own operations and builtins (`extension.CheckToolset`), and records the version each operation joined in (`since`). A toolset only gains operations. The [operations reference](../../reference/operations/#toolsets) lists every bundled toolset with its versions.

**Playbooks declare what they use.** A playbook lists the operations it relies on in its frontmatter (`operations: [github.issue.view, …]`, read by `extension.PlaybookOperations`), and an executor says which playbook a binding config starts its turns on (`extension.PlaybookNamer`; for a package's executor, `executors[].playbook` and `validate` with kind `executor_playbook`). Claude Code and Codex both implement it. `config.GrantWarnings` then reports, for every enabled scope:

- a binding whose playbook uses operations that the binding or its scope doesn't grant, naming the scope, the binding, the playbook and the operations, since its agent would be refused them at run time;
- an operations list that names every operation of an earlier version of a toolset one by one, but not the toolset, and so lacks what the toolset gained since. The warning names those operations and gives the `open-conduit config set` command that grants the toolset instead (the same validated change path as any other edit).

`config check`, `config validate` and `config apply` print them as warnings, and `doctor` shows them as its `grants` check, offline and from the daemon ([doctor](../operator-setup/#doctor)). None of them fails the config.

**Refusals as drift.** Validation records each effective binding's playbook and the operations it declares (`Binding.Playbook`, `PlaybookOperations`), asking each executor once per binding config. When a refused call's operation is one of those, in the generation the call's execution is pinned to, `ConfigService.Refusal` (the daemon's `ToolbeltOptions.Refusal`) classifies it without asking any executor, and its `toolbelt.rejected` record carries `toolbelt.refusal` `config_drift`: the configuration lags what the playbook uses, which is the operator's to fix, not an agent reaching outside its role. Only a refusal of the grant is classified this way. Every other refused call of a genuine token says which authority check refused it: `lease_lost` when the execution's lease has lapsed or moved to a newer epoch (a host that slept or stalled past the lease, before recovery resumes the execution with fresh authority), `token_ended` when the token was revoked (its segment ended, or recovery superseded it) or has expired, `not_running` when the execution or its Work is no longer running, and `not_granted` when the grant or the current ceiling doesn't cover the operation. The caller sees only the refusal, or `authority_recovering` for a `lease_lost` or superseded `token_ended` refusal recovery will undo (step 5 above).

## Configuration and secrets

`config.Validate` strictly parses version 1 JSON: duplicate keys, unknown fields, nulls, types and the 1 MiB limit. It then applies defaults, validates the scope graph, inheritance, tombstones and stable slots, checks registrations and owners, references and authorization, and mechanical capabilities. It returns every independent diagnostic as a safe JSON pointer/code/remedy in deterministic order and never echoes values or reference text. It ports every rule and negative mutation of `scripts/check-config-contract.py`, and the exact invalid-capability diagnostic. A snapshot carries:

- a canonical hash
- redacted normalized config (as written, toolsets unresolved)
- `DomainScopes` (scope metadata without reference text)
- `AuthorizeOperation`/`AuthorizeRead` ceiling checks, on operation lists with their [toolsets](#toolsets) resolved

`config.Resolver` accepts only `keyring:`, `file:` (key in an owner-only `secrets.json`), `env:` and `cmd:`. The default keyring uses the platform helper; tests inject a backend. `cmd:` runs `sh -c` under a 10-second process-group deadline with 64 KiB bounded stdout. Stderr is discarded, the environment is minimal with no toolbelt or Open Conduit variables, exactly one trailing LF/CRLF is trimmed and empty output is rejected. Errors carry stable codes only. No resolution is cached across consumers. `SchedulerOptions.Secrets` resolves only the binding-selected names that both the pinned and the current generation grant. It runs immediately before Run/Recover/Resume, outside transactions; failure blocks that attempt with a safe diagnostic.

`management.ConfigService` restores the committed generation from coordination storage. The first start activates the config file as generation 1. With no config file either, it activates the default configuration (`bootstrap.DefaultConfig`: what `init setup` writes into an empty file, a [setup scope](../setup-sessions/#a-fresh-install)) as generation 1 without writing a file; the first apply writes it. A config file that exists but doesn't validate still stops the start. If the committed generation no longer validates at start (a release stopped registering an operation or executor it names), the config file is published over it as the next generation when the file validates, and the daemon logs the adoption; otherwise start fails naming both errors. Apply proceeds in this order:

1. Revalidate and check the candidate hash and expected generation.
2. Save the file atomically (same-directory 0600 temp, fsync, rename, parent fsync, `.last-good` backup).
3. Publish the generation, its normalized snapshot and changed scope records in one transaction.

A crash before that commit keeps the old generation, and a disk edit alone never changes running behavior. Removing or reparenting a scope with nonterminal Work returns `scope_in_use`. `OnApply` lets the host rebuild generation-pinned components. Toolbelt grants are the pinned binding operations, plus those of the [binding grants](../config-management/#binding-grants) the attempt's Work took, intersected with the current ceiling.

## Local management API

The server implements B05 API version 1 over HTTP/1.1 JSON on an owner-only Unix socket. `AcquireLock` takes an exclusive `flock` and rejects group/world-accessible or foreign-owned state directories. `Listen` removes a stale socket only after lock and ownership checks, rejects over-long paths and sets mode 0600.

Authentication:

- Every endpoint requires a bearer token.
- Operator credentials (digest-only records, bootstrapped under the lock into `private/operator.token`) never reach `/v1/toolbelt/call`, `/v1/toolbelt/guidance` or `/v1/toolbelt/serving`. Execution tokens reach only those endpoints.
- Rotation atomically revokes the caller and returns a replacement once; it is never stored in idempotency history. `RecoverOperator` is the locked local path after a lost response.
- **Roles.** Each operator credential carries a role: `view`, `operate` or `admin`, given when it is issued and kept by rotation. The owner's is always `admin`; a named credential without a role is `view`. The server checks the role where it serves the route, after matching it and before reading the body (`requiredRole`), and refuses with `403 forbidden_role`: reads, route trace and config validate need `view`; config apply and issuing operators need `admin`; every other control needs `operate`. Revoking another operator's credential needs `admin`, which `revoke` checks itself.
- Revocation by token ID covers execution tokens, the caller's own operator token and, for an `admin`, any named operator's. The owner's own credential (the state directory's) is revoked only by itself or by `RecoverOperator`, so no named operator can lock the owner out.
- An operator credential names its operator. The state directory's is the owner's, `local`. `POST /v1/auth/operators` issues one for a named operator (`[a-z][a-z0-9-]{0,31}`, not `local`, one active credential per name) and returns its token once, uncached and never stored in idempotency history, as rotation does. `GET /v1/auth/operators` lists every credential by name and role, without tokens. `BootstrapOperator` looks only at the owner's credential, so a named operator's never stands in for a missing token file.
- **Every operator is recorded as itself.** The server puts the authenticated principal (`operator:<name>`) on the request context (`runtime.WithActor`), and `runtime.Control` stamps it as the `Actor` of every `core.manual` Event it accepts. Actions are invoked with the same principal as `Caller`, and `Control.Act` stamps the caller on the `core.action` Event. Acceptance (`AcceptInTx`) drops the `Actor` of an Event from any other source, so only the host can say who did something.

Request handling:

- Mutations require `application/json`, a body of at most 1 MiB, strict fields (no unknown, duplicate or null fields) and no query string.
- Every mutating POST except validate, rotate, operator issue, route trace and toolbelt calls requires `Idempotency-Key`. The key is bound to principal, method, path and canonical body hash, and kept for 30 days. A named operator's key is prefixed with its principal before anything derives an identity from it, so two operators' requests under the same key never meet; the owner's keys are unchanged. A replay returns the original status and body; a changed body is `409 idempotency_conflict`.
- Operator actions derive durable identities from the key, so retrying a timed-out request completes the same operation.
- Opaque IDs may contain `/`. Routes match escaped path segments.

Reads:

- Lists use HMAC-authenticated cursors bound to endpoint, filters, a captured upper bound and a 15-minute expiry. Events use acceptance-sequence keyset traversal; other primitives use `(created_at,id)`.
- Single reads expose revision ETags and answer `If-None-Match` with 304.
- Errors use the B05 envelope with safe codes and never include backend/provider text.

Operator controls go through `runtime.Control`:

- **Manual events**: `core.manual` root, or a derived event when a readable parent is supplied. Routed immediately when possible.
- **Manual Work**: atomic ready Work, root `core.work.created` and explicitly bound queued input. Nothing is launched directly.
- **Work cancel**: a control Event plus full fencing in one transaction.
- **Execution cancel**: fences one attempt and holds scheduling (`BlockedReason=operator_cancelled`) until a manual retry. Physical stop still needs trusted `ConfirmStopped`.
- **Retry**: `core.manual.retry` processed by retry policy.
- **Wake**: an ordinary owned-key event that reports whether it matched.

**Route trace.** `POST /v1/scopes/{id}/route/trace` takes a hypothetical Event (`type`, optional `source`, which defaults to `core.manual`, `correlation_key`, `work_id` and `data`) and returns how the router would handle it now, against the active generation and current Work state. It returns each effective route in order with its verdict (`match`, `skip`, `not_reached`, or `bypassed` when the Work is waiting or finished) and the handler's reason, the Work the Event resolves to, and the `effect` (`start`, `queue`, `inject`, `interrupt`, `wake`, `drop` or `unmatched`) with a short detail. `also` lists other wakes: Work it would wake through a dependency subscription, or another input waking its own Work first. Nothing is accepted, routed or recorded, so it takes no `Idempotency-Key`. An Event acceptance would refuse is refused with `422 invalid_request` rather than explained: a type or payload schema that is not namespaced, data that is not JSON, a core type or a core source other than `core.manual` and `core.action` (an operator's Event and an action's, which the host accepts for the operator; `runtime.CheckTraceEvent`), a registered source that belongs to another scope (`Ingress.AdmitsTrace`), a package payload the package may not write, and an unknown source: one that is not `core.manual`, no ingress registers and whose type no package owns. `GET /v1/scopes/{id}/route/samples` lists the named sample Events the scope's route handlers offer, so a view can show "Suppose…" choices without hard-coding them. `open-conduit route --trace TYPE|SAMPLE --scope S` and `route --samples --scope S` call these endpoints.

Rebind, hold/release, attach and scope reconcile are described in [operator setup and controls](../operator-setup/).

Control checkpoints keep the Work in the envelope but use an empty routed association, so earlier runnable input cannot delay fencing. `artifacts/{id}/content` streams through `storage.Artifacts` and supports one byte range.

The client dials only the configured socket, with the fixed host `localhost`, no proxy and no redirects. `open-conduit` resolves the endpoint (`--endpoint`, then `OPEN_CONDUIT_ENDPOINT`, then socket discovery) and the token file (`--token-file`, then `OPEN_CONDUIT_TOKEN_FILE`, then `state/private/operator.token`). It supports, among other commands:

- health
- scopes, work, events (including causal `events chain`), executions, waits and artifacts (`artifacts cat` for logs)
- emit, work create/cancel/retry/wake and execution cancel
- config validate/apply
- auth rotate/revoke, and auth operators/add for named operators
- unified run history (`runs list|get|table|log`), `doctor` and `tui` ([observability and history](../observability-history/))
