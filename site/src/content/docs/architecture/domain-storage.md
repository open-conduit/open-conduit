This page records decision B02: the public Go records for the five primitives and the storage contract every backend must keep, covering identity, lifecycle, transactions, lease fencing, timers, waits, KV, artifacts and schema compatibility. The records are in [`domain`](https://github.com/open-conduit/open-conduit/blob/main/domain/types.go) and the contract in [`storage`](https://github.com/open-conduit/open-conduit/blob/main/storage/storage.go). [Shared cases](https://github.com/open-conduit/open-conduit/blob/main/conformance/storage.go) check any backend; they run against a [volatile reference double](https://github.com/open-conduit/open-conduit/blob/main/conformance/reference/memory.go) and against the production SQLite backend and file artifact store ([SQLite and artifacts](../sqlite-artifacts/)). [Negative controls](https://github.com/open-conduit/open-conduit/blob/main/conformance/storage_test.go) prove the cases catch broken backends. Runtime behaviour above this boundary (routing, waits, retry, causation) is [B04](../runtime-semantics/).

## Records and identity

There are five primitives: Work, Event, Execution, Timer/Wait and Scope. Supporting values (IDs, revisions, bindings, outcomes, leases, matches, artifact references) are not additional primitives.

- IDs are opaque, nonempty strings, allocated by the caller before a transaction. Work and Execution IDs are never reused. Revision zero means “create if absent”; updates supply the exact persisted revision. The backend assigns revision and creation/update timestamps from the trusted transaction clock. A Work's `UpdatedAt` is never earlier than one already committed, even when the clock steps back: the backend takes the later of the transaction's clock and the latest stamp, under the writer. So a reader that lists Work changed since the latest change it saw (`storage.LiveOrChanged`, #707) misses none (`work_changes_stamped_in_order_across_clock_step_back`). Supplied record revisions/timestamps are not authority. Returned values, including slices/maps/JSON, are detached copies.
- Work kind and Event type are opaque dotted namespace identifiers. Payload has a namespaced schema identifier and valid JSON bytes; an absent payload is permitted. The core does not inspect domain fields. These Go records do not define the subprocess wire protocol; payload schema evolution for extension payloads is defined in [the extension protocol](../extension-protocol/#event-payload-schema-evolution), and envelopes stay immutable.
- A correlation key is `(source, external_id)`. Source must identify the external account/resource namespace, not merely the service name. A key has at most one owning Work, across scopes and terminal states. Work can append keys; it cannot remove or transfer them. Conflicting create/attach fails atomically. Correlation is not event identity. Shared prerequisite subscriptions must not steal another Work's key: [B04](../runtime-semantics/#wait-registration-observation-and-exactly-one-wake) defines subscriptions/alias events and adapters supply dependent correlations.
- Work kind, scope and parent are fixed at creation. Parent must already exist; child creation cannot introduce cycles because parent links are immutable. Terminal Work remains an ownership tombstone so replay cannot accidentally create a new objective for an old key. Reopening external work needs an explicit extension policy ([B04 successor rule](../runtime-semantics/#routing-and-ownership)); it cannot silently rewrite terminal records. A later distinct objective needs distinct identity/correlations or a reviewed contract change.
- Event envelopes are immutable, including an absent Work ID. Acceptance returns the stored envelope and `added=false` for duplicate `(source, delivery_id)`, even if the retried request uses another internal ID/correlation. An existing internal ID for a different delivery conflicts. Different deliveries sharing a key are all retained. Derived Events reference an existing causation Event, which prevents dangling/cyclic causation; mandatory derivation checks and chain limits are runtime contracts ([B03](../extensions/), [B04](../runtime-semantics/#causal-bounds-and-rejection-evidence)).
- An Event's `Actor` says who caused it, as `kind:id` (`operator:alice`, `github:octocat`), when the host knows. The host sets it from the operator credential on `core.manual` Events and from the caller on `core.action` Events; acceptance drops it from an Event of any other source. It is part of the immutable envelope, and record format 2 added it. Record format 3 added a binding's `PassEnv` to the binding an attempt pins. Record format 8 added `Requires.NoProcess`, the executor capability a scope that requires isolation reads, to a stored binding. An Event's `Via` is the client its `Actor` acted through, when a client credential acted for the person signed in to it (`operator:acme-ui`); it is set and dropped with `Actor`, and record format 7 added it. The shared storage suite's `event_actor_round_trip` case proves a store keeps both through acceptance, `Event`, `Events` and a duplicate delivery.
- An accepted Event's `ScopeID` is the Scope the runtime accepted it into. The runtime records it with `SetEventScope` in the transaction that accepts the Event, and it is write-once: the same scope again is a no-op, another conflicts, and an empty one is invalid. It is storage metadata beside the envelope, like the routing checkpoint, so it survives routing and comes back on a duplicate delivery. It is empty only for an Event storage accepted on its own or one accepted before record format 4 added it; the daemon backfills those at startup (`Router.BackfillEventScopes`) from the acceptance record or the Work the Event's identity resolves to, so an Event's scope is fixed where it was accepted rather than worked out again on every read.
- An Execution's `Artifacts` are its outcome's, the latest turn's result's. When a later turn's result replaces them, the runtime moves the earlier turn's to `EarlierArtifacts`, so `AllArtifacts` is every artifact the attempt published; collection, backup and retention use it. Record format 6 added `EarlierArtifacts`, and the artifacts each of an attempt's segments published. Record format 7 added each reference's `SHA256`.
- Scope supports parent, routes, bindings, opaque config and secret references without requiring any workspace. Parents must exist; scope updates cannot form cycles. Inheritance/merge, reload validation and secret resolution are defined by [B05](../config-management/), not by the storage contract. [B04](../runtime-semantics/) fixes route ordering/overrides and binding lookup; B05 supplies configuration syntax and reload/auth. Bindings expose mechanical requirements only; no semantic suitability claims.

## Work and Execution lifecycle

Same-state Work updates are allowed for nonterminal records; a same-state write still checks and advances revision. Terminal records are immutable. The transition predicates describe actual state changes, so equality is not a transition.

| From Work state | Allowed next states |
| --- | --- |
| ready | running, failed, cancelled |
| running | ready, waiting, completed, failed, cancelled |
| waiting | ready, running, failed, cancelled |
| completed / failed / cancelled | none |

A failed Execution does not itself fail Work. Retry policy returns Work to ready and arms a backoff timer while automatic retries remain. The default stops automatic retries at exhaustion but keeps Work nonterminal so a manual event can request attempt N+1; an explicit terminal-failure policy may instead mark Work failed. The runtime commits those choices with the failed attempt and routing progress in one transaction. Attempt counters start at 1 and advance without gaps; no second nonterminal attempt for one Work is allowed. Work may remain ready pending capacity or a retry timer. Retry eligibility and the backoff delays are runtime policy ([B04](../runtime-semantics/#lease-recovery-retry-and-cancellation)), not storage-side scheduling.

| From Execution state | Allowed next states |
| --- | --- |
| pending | running (Claim only), cancelled |
| running | parked, completed, failed, waiting, handoff, cancelled |
| parked | running (Claim only), failed, cancelled |
| completed / failed / waiting / handoff / cancelled | none |

Execution outcome kinds are completed, failed, waiting and handoff. Completed/failed/handoff terminal states require their matching outcome. Pending/running/cancelled have no outcome. `parked` is nonterminal with waiting outcome for a resume-capable executor; terminal `waiting` is the outcome for an executor without resume. Both release authority. Wake is an accepted Event; it resumes the parked attempt through a new Claim or creates attempt N+1 after terminal waiting. No direct wake bypass exists in this storage API. Resume capability is checked when a binding is validated ([B03](../extensions/#executor-lifecycle-and-continuity)), with wake matching/race semantics in [B04](../runtime-semantics/#wait-registration-observation-and-exactly-one-wake).

Handoff terminates an attempt and returns Work to ready under policy; it does not imply completion of Work. Continuity data remains in executor-owned namespaced KV or opaque outcomes. Cancellation is an explicit Work transition and invalidates execution authority immediately at the serializable transaction boundary; control-plane code cancels the attempt, marks/cancels waits and removes timeout/retry timers before setting the terminal Work state in the same transaction. Any process interruption happens after that commit. Stale completion cannot reverse cancellation. Operator retry of exhausted but nonterminal Work creates the next attempt. Explicitly terminal failed Work needs a successor Work rather than mutation; the failed record is preserved. [B04](../runtime-semantics/) requires a distinct generation-qualified successor key; terminal correlations never transfer.

Claim assigns first-start time; terminal Execution writes assign finish time. Parked/resumed execution keeps its original start and no finish until terminal. All executor types use the same attempt record, trace ID, outcome and artifact references. Retention selection is generic runtime policy ([retention](../observability-history/#retention)).

## Retired Events

`Tx.RetireEvent` moves a routed Event out of the live log and leaves a tombstone: its envelope and routing metadata without its payload, marked `Retired`. It is the storage primitive the history archive builds on, and nothing calls it in production yet. `Event` and `EventByDelivery` answer with the tombstone, so a redelivery stays a duplicate, its ID and delivery stay taken, by a new Event or a Timer's, and a new Event, a Timer, an attempt's trigger or a Wait's wake can still cite it. The list reads omit it, as a gap in the sequence, and `LatestSequence` never goes back past it, so Wait boundaries and extension cursors hold when the newest Event is the one retired. Its routing and scope stay fixed. `Tombstones` lists them in sequence order, so a backup can walk them beside the archive in constant memory and prove the archive holds what each stands for. An unrouted Event can't be retired. Over the extension protocol a tombstone carries `retired: true`, so an extension can tell a released payload from an empty one. The shared case `retired_event_keeps_identity_and_sequence` proves this, with a store that forgets the tombstone on redelivery, one that reads the latest sequence from live rows, and stores that check a Timer, attempt or Wait against live rows alone as negative controls.

`runtime.RetirementGuard` says which Events the live system no longer decides with. Nothing calls it in production yet. It is built in the transaction that retires them, and it keeps these in the live log:

- an Event an operator can still route again (`failed` or `skipped`), because the copy carries its payload;
- an operator control or action, because its replay answers from its payload;
- a Work's creation Event and a once-only emission, because a repeat is compared with their payload;
- any Event of unfinished Work, and the trigger, inputs and wake of its attempts, wherever they were routed;
- anything past the oldest position an active Wait or dependency has yet to scan, because it could still wake it.

A dependency declared without `FromNow` scans all accepted history, so that a state already met counts, including one whose Event has been retired. It catches up from the archive: the subscription is installed first, which pins every Event after its checkpoint in the live log, so the archived records it needs can no longer change. They are read by correlation key outside any transaction and merged with the live log by sequence in the write transaction, so its filter sees whole records and no write waits on the archive. If the archive can't be read, the checkpoint stays where it is and the next pass reads again, because scanning the live log alone would pass an archived Event by for good.

## Event archive

`storage.EventArchive` holds the whole records of Events that have left the live log, behind `storage.EventArchiveBackend`. The daemon opens the built-in one at `archive/` in the state directory. The order it is built for is to copy an Event with `PutEvents`, which is durable when it returns, and only then retire it, so a crash between the two leaves the Event live and the pass runs again. A record the archive already holds is nil, compared by value (`storage.SameAcceptedEvent`: the same instants in any zone, the same payload JSON), so a pass that crashed can run again under a newer binary. A different record under a held ID or sequence is `ErrConflict`, and a tombstone or unrouted Event is `ErrInvalid`, in both cases storing none of the batch. `Events` and `WorkEvents` read in sequence order, however the archive is partitioned. The built-in backend (`sqlite.ArchiveBackend`) keeps one private SQLite file per UTC month of `ReceivedAt` in a directory it holds an exclusive lock on, and a small `index.db` mapping each ID, sequence and Work to its month. A read asks the index and opens only the months its page falls in, so its cost doesn't grow with the archive's age and idle months hold no file open. A record and its index entry commit together, in one SQLite transaction across the two attached files. `conformance.RunEventArchive` proves the contract, with a weakened archive as the negative control for each case.

`storage.EventHistory` reads across the live log and an archive, for the reads that show history: the management API's Event list and single read (so `events chain` too) and an extension's `state.event`, `state.delivery`, `state.events` and `state.work_events`. It merges both by sequence, so a cursor pages across them exactly as it pages the live log. It reads the transaction's view first and the archive after it. An Event is archived before it is retired, so everything that view sees as retired is already there. A record in both, from a pass that stopped between copying and retiring, is answered once, and a record past the view's latest sequence is left out. A tombstone's recorded scope stands over the archived copy's, because authority is decided on it, and a sequence that disagrees is an error. A failed archive read is an error too, never a page with a silent gap. With no archive, or for a tombstone the archive doesn't hold, the read answers from the live log, with the tombstone still marked `Retired`. The runtime's own decisions keep reading the transaction alone, so no write waits on an archive. Run views show an Event's envelope, which a tombstone keeps, so they need no archive read.

`Scheduler.ArchiveEvents` is the pass that moves finished history. The daemon runs it from the retention pass, up to ten pages each time, once `settings.archive_finished_days` is set; unset, nothing is archived. It stays off by default because how long history stays in the live database is the operator's choice, and turning it on moves that history out, so it shouldn't happen as a side effect of an upgrade. `settings.archive_unmatched_days` is the horizon for Events that opened no Work, and defaults to the same value. Each pass updates a record in the live database (`core.archive`) with how many Events have moved and, for the last whole trip over the log, why the others stayed live, including those a Wait still pins. `doctor` reports it as the `event_archive` check, and each pass emits an `events.archived` telemetry event. It takes Events of Work that finished by one horizon and Events that opened no Work by a shorter one, and only those whose scope is recorded, since recording a scope later would change the record the archive holds. It reads a bounded page from a rotating cursor, so an Event kept today is looked at again and a pass costs the same however long the log is. It copies the page to the archive outside any transaction, then retires in one transaction that rebuilds `RetirementGuard` and decides again, leaving live anything that changed or became needed meanwhile. A crash at any point leaves each Event live or archived, and the next pass completes it. A failed copy retires nothing. A record that conflicts with the archive's copy stays live and is counted, so it can't hold up the rest of the page. The pass returns how many Events it moved and, by reason, how many it kept. A timer firing replayed after its Event was retired answers with the tombstone, which is safe because the daemon uses only the number of firings.

### Compaction

Archiving frees pages inside the database, which SQLite reuses before it grows the file. `storage.Compactor` is the optional contract for giving them back to the disk: `Space` reports the file's size and free space, `Reclaim` returns some free space while the database is in use, and `Rebuild` rewrites it. A backend without file space to manage doesn't implement it.

SQLite can only return pages a few at a time in `auto_vacuum=INCREMENTAL` mode, which a database has to choose before its first table or take on through a full `VACUUM`. New databases are created in that mode. With `settings.archive_finished_days` set, the retention pass returns up to 64 MiB each time, leaving the larger of 16 MiB and 5% of the file free, so pages about to be reused aren't handed back and allocated again. An older database is rebuilt once, at a daemon start before any package runs, when at least 64 MiB and a quarter of its file are free, because `VACUUM` holds up every write and needs room for a copy. The attempt is recorded in the live database first. If it fails, or the process dies during it, the start goes on, the free space stays in the file for reuse, `doctor` shows the cause under `event_archive`, and no start tries again for seven days. Each compaction is logged and emits a `database.compacted` telemetry event, and a failed rebuild emits `database.compaction_failed`.

## Transactions and checkpoints

`Store.Transact(ctx, Guard, callback)` is the only coordination mutation boundary. It is serializable and a backend invokes the callback once, without transparent callback retries. Callback error, panic (propagated) or context cancellation before commit leaves no writes. All callback operations are short local computations; no external writes, network calls or executor launch inside a transaction. Commit cannot roll back a service side effect.

Two refusals look alike and mean different things. `ErrConflict` is a clash over records: a stale revision, an owned correlation key, a write-once field set otherwise. Running the same logic over the same records again cannot cure it, and the runtime acts on it (a renewal refused that way ends the attempt's hold as lease lost). `ErrTransient` is an abort that says nothing about the records: a serialization conflict with a concurrent transaction, a lock not taken in time (SQLite's busy and locked). A backend returns it, from any call or from `Transact` itself, only when nothing committed; one that cannot tell whether a commit took effect must not. `storage.Retry(store, policy)` is the one retry policy: a `Transact` or `View` that fails with `ErrTransient` runs again, callback and all, so the callback rereads the state and decides afresh, up to `policy.Attempts` runs with `policy.Backoff` between them (`storage.DefaultRetry`: five runs, about 5, 10, 20 and 40 ms apart), and every other error is returned as it is. A callback run under it may run more than once and only its last run commits, so it must set, rather than accumulate into, what it hands back, and decide any effect after the transaction from the last run alone. The daemon wraps its backend in `storage.Retry(store, storage.DefaultRetry)` at its composition root, beneath `Instrument` and everything that transacts, and logs a transaction that aborted on every attempt. SQLite returns `ErrTransient` only when a lock is not taken within its busy timeout, so in practice that is another process holding the database's lock, which the backend's ownership of its location prevents. The SDK's protocol store is a backend of the same kind: its transaction commits as one `kv.commit` whose preconditions are the keys it read, and a commit refused because one of them changed applies nothing and is `ErrTransient`, so the in-process bridge, `Host.Update` and the extensions that open one run it under `Retry` too, while a refusal rereading cannot cure stays `ErrConflict`. Every callback in the tree is held to the rule by a harness rather than by audit: built with `-tags rerun` (`make test-rerun`), the SQLite backend and the reference store run each `Transact` and `View` callback once, abort that run with `ErrTransient` and let `Retry` run it again, so the unit suites fail on any callback that accumulates across runs or runs an effect inside its transaction; each harness has a negative control (`TestRerunCatchesAccumulatingCallback`) showing an accumulating callback caught. The storage suites themselves are left out of that run, since they hold a backend to running a callback once. A renewal that fails with `ErrTransient` is reported and renewed again on the next tick, never taken as a lost lease. The shared case `transient_aborts_commit_nothing_and_retry` runs contenders that read and increment one KV counter through `Retry`: the counter must end at the number of contenders and no contender may be refused. Its negative controls are a store that reports contention as `ErrConflict` and one that returns `ErrTransient` after committing.

A backend may also be a `storage.Viewer`: `View(ctx, callback)` reads a consistent snapshot of committed state, outside any `Transact`. It refuses every write with `ErrReadOnly` (`storage.ReadOnly` wraps a transaction that way) and keeps nothing the callback does. Views run alongside each other and alongside an open `Transact`, never wait for it to commit and never see its writes. `storage.View(ctx, store, now, callback)` reads through a backend's `View` when it has one, and otherwise in a `Transact` whose writes are refused, which waits its turn; so a store an extension implements over the protocol needs no `View` of its own. Management serves every read through it, so an operator's view never queues behind the runtime's writes or other reads. The shared storage suite's `view_reads_committed_state_alongside_writes` case proves the snapshot, the refusals and, for a `Viewer`, that a View completes while a write is held open; its negative controls are a View that serialises behind writes and one that writes.

A successful production transaction acknowledges only after durable commit. The reference double serializes transactions and copies state on commit; it intentionally cannot prove crash durability or throughput. It does not implement scheduling, routing handlers, process adoption, SQLite or network management. A transaction and its Tx must not escape or be used by concurrent goroutines/nested transactions.

One transaction can include Event acceptance, Work create/correlate/revision update, route progress, Execution creation/claim, Wait registration, Timer changes and namespaced KV. Per-operation validation errors must be returned by the callback. The API distinguishes:

1. **Acceptance checkpoint:** commit Event before acknowledgement or route execution. `AcceptEvent` returning within a callback is not a durable acknowledgement; the outer transaction must succeed. A newly accepted Event has an acceptance sequence greater than any before it (gaps allowed) and no routing checkpoint. Sequences become visible in sequence order: a reader that sees sequence *n*, through an event read or `LatestSequence`, already sees every Event below *n* that will ever commit, so an exclusive cursor or a Wait's boundary (`AfterSequence`, taken from `LatestSequence`) never skips an Event that commits later. A backend serialising its writers keeps this by assigning sequences in commit order. One that allocates them before commit, as an identity column under concurrent writers does, must hold readers back to the highest sequence below which every allocation has committed or rolled back. The shared case `sequences_visible_in_order_to_a_waiting_reader` needs to know which kind of backend it is checking, so a backend under the suite declares through `conformance.WriterAdmission` (`SerialWriters() bool`) whether it admits writers one at a time; a store that declares neither fails the case. The case holds one writer open while a second accepts an Event. A backend that admits writers together must commit the second while the first is open (only a failing backend reaches the deadline), and a reader then takes its cursor; the page after it must hold the first writer's Event once it commits. A serial backend holds the second writer, so it gets only that final check, with no waiting. The reference double and `sqlite.Store` declare serial. Its negative control declares concurrent writers, allocates sequences at acceptance and shows them at commit.
2. **Processing checkpoint:** a later transaction commits route effects and `MarkRouted(event, work, disposition)` together. Routing association/disposition are separate metadata, never edits to the Event. Same checkpoint replay is idempotent; changing an already committed association/disposition conflicts. Drops and unmatched Events retain a disposition for audit.

A crash after acceptance leaves an unrouted Event to replay. A crash during processing leaves either every effect/checkpoint or none. Global sequence supports replay pagination, not global routing serialization. Route progress for one Work follows acceptance order for Events explicitly targeting it or currently resolving through its keys; independent Work has no global processing dependency. [B04](../runtime-semantics/#routing-and-ownership) specifies ordering for concurrently attached keys, previously unresolved Events and multiple route handlers.

Enumeration of scopes, Work, attempts, timers and waits enables recovery without process-private indexes. Returned lists are sorted by ID; execution/wait scans may filter by Work (empty means all). Events are sorted by acceptance sequence, with exclusive cursor and optional positive limit. The same scan restricted to unrouted Events, the unrouted Events that could be input to one Work (`UnroutedInput`: those naming it, naming one of its attempts or carrying one of the keys the caller gives, between two sequences), the unrouted Events of given types (`UnroutedOfType`), the same scan restricted to one Work's Events (`WorkEvents`: those naming it and those routed to it, each once), the same scan restricted to Events recorded in given Scopes (`ScopeEvents`, where an empty ID asks for the Events with no scope recorded yet), the latest accepted sequence and lookup by delivery identity are separate reads, and so are `LiveWorks` (Work not yet finished), `LiveExecutions` (attempts pending, running or parked) and `ActiveWaits`, so routing, scheduling and a view of one Work never need to read retained history. The shared storage suite's `live_reads_follow_state` case proves the live reads follow every state change, `work_events_follow_naming_and_routing` that a Work's Events are exactly those naming it or routed to it, `event_scope_recorded_once_and_indexed` that a recorded scope is write-once, survives routing and duplicate delivery, and selects exactly the Events `ScopeEvents` returns, and `unrouted_input_follows_work_attempts_and_keys` that `UnroutedInput` and `UnroutedOfType` return exactly the Events they select, with a store that misses input naming an attempt as its negative control. Routing makes the `UnroutedInput` read for every Event it routes, and the scheduler the `UnroutedOfType` read every pass, so their cost follows one Work's input and the scheduler's own Events, not the unrouted backlog (#705). Operator views select Work through `QueryWorks`, `CountWorks` and `WorkFacets` (a `WorkQuery`: any of some states, a scope, kind, parent, any of some sources, the latest attempt's executor and an updated-since time; ordered by creation or update time to the nanosecond, then ID, either way; paged after a `WorkKey`), whose cost follows the Work they select, not retained history. A Work's source is the source of its first correlation key other than its lineage key (`domain.SubjectKey`; the host adds `core.work`/`<its ID>` when the Work first waits with no key or asks for child Work, and that names only the Work), else its kind, so it doesn't change partway through the Work's life. Each attempt records the executor its binding named (`Execution.Executor`), and storage keeps its Work's `LatestExecutor` as attempts are registered, ignoring a writer's value as it does the timestamps. Attempts registered before it was recorded have it set once from their own state through the write-once `SetExecutionExecutor` (the runtime's `BackfillExecutors` runs at startup), which updates the Work's `LatestExecutor` when the attempt is its latest; an update that leaves an attempt's executor empty keeps it. `storage.SelectWorks` gives the queries' meaning over a plain list. A finished attempt is otherwise immutable, but `PublishFinishedArtifacts` lets it take the artifacts of the turn it was fenced during, which that turn's process wrote once it stopped. It applies the publish rule `storage.PublishedArtifacts` gives (the refs become its `Artifacts`, the ones it held move to `EarlierArtifacts`) whatever its Work's state, since a cancel finishes the Work with the attempt. It changes nothing else but the revision and update time, and the same refs again change nothing. The `finished_attempt_takes_its_stopped_turns_artifacts` case proves it, with a store that drops the earlier artifacts and one that refuses a finished Work as its negative controls. `ReferencedArtifacts(ids)` is the reverse lookup artifact collection needs: of up to 1000 artifact IDs (a `List` page), the ones some attempt references as one of its `Artifacts` or `EarlierArtifacts`, each once in byte order, at a cost that follows the IDs asked about rather than the attempts retained. The `referenced_artifacts_follow_attempts` case proves it through a transaction and a View, across a rolled-back attachment and a later turn's refs, with a lookup that misses earlier artifacts and one that neither groups nor sorts as its negative controls. The `work_queries_select_order_page_and_count` case proves each filter, both orders across time zones with ties broken by ID, keyset paging, counts and facets, that the executor is the latest attempt's and kept by storage, and the write-once rule. All reads/scans return backend errors. A backend may add pagination and index selection without weakening these guarantees.

## Lease authority and recovery

`Guard.Now` is trusted runtime time, fixed at a transaction's serializable admission point; executors cannot supply it. Runtime supplies a nondecreasing UTC clock. Lease expiry is exclusive: `Now == ExpiresAt` has already expired. The production backend must preserve this admission/commit ordering under competing connections; the SQLite backend's tests cover competing connections and process death ([SQLite and artifacts](../sqlite-artifacts/#evidence)).

Claim enters running for Work and Execution and assigns owner, expiry and a strictly increasing per-Execution epoch. A live lease rejects competing Claim. An expired or explicitly released lease permits recovery of that same attempt with a higher epoch, even for the same owner string. Claim alone does not prove an old process can be adopted: runtime/executor recovery first determines whether to adopt or record a failed attempt ([B03](../extensions/#executor-lifecycle-and-continuity), [B04](../runtime-semantics/#lease-recovery-retry-and-cancellation)). Storage never reads session/process metadata.

Every executor-originated transaction supplies its lease reference in Guard. Before its callback can mutate anything, the store verifies Work is nonterminal, Execution is running, owner/epoch match and expiry has not passed. This fences all writes, including Work/context, emissions, outcomes, timers and KV. Epoch/owner/expiry cannot be changed by PutExecution. Renew and Release check the same authority; renew cannot shorten or revive an expired lease. Release clears owner/expiry but preserves epoch; parked/terminal transitions also release it. A nil Guard lease is trusted control-plane authority, never the public toolbelt default. Scope/token authorization is the layer above this contract ([B03](../extensions/#toolbelt-authority-and-registration), [B05](../config-management/)).

## Timers, waits, reconciliation and KV

A Timer stores a fire time and Event template. Fire fills occurrence time with the due time and receipt time with the trusted clock. `FireTimer(id, revision, next)` accepts that Event and either removes a one-shot timer or rearms the same timer ID in one transaction. Recurrence calculation is extension-owned; next time must be later and its Event identity must differ. Timer templates cannot reuse already accepted Event identities. Early/stale fires fail. KV cursor updates join the same transaction; crash recovery cannot commit a recurrence cursor without its Event.

Timer revisions stay monotonic across deletion/recreation, so an old fire command cannot operate on a replacement timer with revision 1. Timer deletion requires the current revision. Any compacted revision tombstone must preserve that guarantee. A next occurrence may already be overdue when rearmed; the schedule extension applies missed-slot policy. The storage layer has no clock polling loop; the runtime's timer scheduler fires due timers ([timers and waits](../timers-waits/)).

Wait registration stores Work/Execution identity, keys/type filters, an exclusive acceptance-sequence boundary and optional timeout Timer ID. It must join the transaction parking the attempt, releasing authority and marking Work waiting. Its keys belong to that Work; the reference double rejects foreign matches. Timer presence is required at registration only; a timeout can fire/delete before the historical Wait transitions. The predicate/boundary/timeout, description and owner are immutable after registration. While a Wait is active, the only other write changes the progress line of a Wait that has an owner (the extension that declared it); its state changes once from active to woken (with an existing accepted Event ID) or cancelled, keeping its progress; the storage layer checks identity/revision, while [B04](../runtime-semantics/#wait-registration-observation-and-exactly-one-wake) specifies matching, already-observed events, boundary races and timeout tie-breaking. A wake transaction records the winner, consumes/cancels the timeout and updates Work/Execution together. History remains inspectable.

Namespaced KV provides get/put/delete/list-by-prefix; namespaces/keys are nonempty and delete of an absent key is safe. Keys compare as bytes: a prefix matches byte for byte, so `%`, `_` and `\` in it match only themselves, and a list is in byte order, never a collation's (upper case before lower, ASCII before multi-byte UTF-8, case never folded). The shared case `kv_prefixes_and_order_are_bytes` proves both, with an unescaped `LIKE` match and a case-insensitive order as its negative controls. Results and values are copies. KV is for coordination: executor-private continuity, observations, cursors and small extension state. Reconciliation stores per-source/scope observation and cursor keys with resulting Events in one transaction. A page cursor may advance only for durably accepted page changes; snapshot completion controls absence detection. The observation/completeness schema and push overlap are [B03](../extensions/#ingress-identity-observations-and-recovery). No large logs, indexes or artifact bytes in KV. External stores are explicit extension connections.

## Audit ledger

`AppendAudit(record)` adds a `domain.AuditRecord` to the audit ledger in the caller's transaction and returns it as stored, and `AuditRecords(after, limit)` reads the ledger in sequence order, exclusively after a sequence. Storage owns four fields and ignores a writer's values for them:

- `Sequence`: one past the last record's, 1 for the first. The ledger has no gaps, so a rolled-back append takes no number, unlike an Event's sequence.
- `At`: the transaction's `Guard.Now`.
- `Prev`: the last record's `Hash`, empty for the first.
- `Hash`: the record's `Digest()`.

`domain.SealAudit` does all four, so every backend chains the same way. A record without an `Action` or `Outcome` is `ErrInvalid`, a `View` refuses the append with `ErrReadOnly`, and records are never changed or removed. The SQLite backend keeps the ledger in its own table, created on every open as its indexes are. A database an earlier binary made therefore gains it without a schema change, and an earlier binary that opens it appends nothing, which leaves the chain whole. The extension protocol's store refuses both methods: an extension reads the ledger through the management API. The shared case `audit_ledger_numbers_chains_and_pages` checks numbering across a rollback, the chain (`domain.VerifyAuditChain`), every field kept, paging and both refusals. What the host records there is in [observability and history](../observability-history/#audit-ledger).

## Artifacts and local state compatibility

Artifacts are separate from the coordination transaction. `Create(mediaType)` yields a streaming writer; `Commit(ctx)` closes/publishes immutable bytes and returns an `ArtifactRef`: an opaque ID, the size, the media type and the content's SHA-256 (`SHA256`, 64 lower-case hex characters). The digest travels with the reference (in the Execution record, on the extension protocol as `sha256`, in a bundle's manifest and in the management API), so any backend, bundle or reader can verify the bytes without the backend's own metadata. An extension built on an SDK that predates digests returns `artifact.commit`'s reference without it; the host fills it in before it records the result, reading the content to its end (which the store verifies) and refusing a reference that names no stored content. So a recorded reference lacks the digest only if it was recorded before record format 7. Those stay in history, so a store must still open a reference without a digest, verifying it against what it recorded itself, as long as its other fields match; the artifact suite requires it. Close without successful Commit aborts; repeated commit and write after close return an error (the file artifact store returns `ErrClosed`). `Open` takes only the reference Commit returned (another size, media type or digest is `ErrInvalid`, an unknown ID `ErrNotFound`) and returns a streaming reader that checks the size and digest as it goes, returning `storage.ErrCorrupt` in place of EOF when they don't match. Delete is idempotent, and refuses a reference that doesn't match the stored content. References live on the durable Execution record; they are not an Effect primitive.

Everything participants publish and read goes through `storage.Artifacts`. A backend's whole store is a `storage.ArtifactStore`, which adds what the host needs to back it up, restore it and collect what nothing references: `List(after, limit)` pages committed content in ID byte order with each reference and its publication time, never listing unfinished, aborted or deleted content, and `Import(ref, source)` publishes a source as exactly that reference, ID and all, or nothing when the source runs short or long or misses the digest (`ErrCorrupt`), or the ID is already there (`ErrConflict`). An `ArtifactBackend` opens a store from a location in its own terms, and `storage.RegisterArtifactBackend` makes one selectable by name, as `RegisterBackend` does a coordination backend; the file store is `files`. Nothing in the contract rests on a process-local lock: a backend may let several processes or hosts open one location (an object store does), or refuse a second owner (the file store owns a local directory), and either way an unfinished write a dead process left is never readable or listed and the backend clears it up itself. Retention, orphan collection and backup work over this contract alone, so no backend needs a lock: a backup holds content from retention with a hold in coordination, and collection pages the store with `List` and asks `ReferencedArtifacts` which IDs of a page are referenced ([retention](../observability-history/#retention)). The daemon and the offline commands open the store the state directory's `storage.json` names ([backend lifecycle](#backend-lifecycle)).

Publish first, then attach the reference in a coordination transaction. If attachment rolls back or the process dies between these steps, published content may be orphaned and is eligible for age-based garbage collection. A failed/ambiguous publish returns no usable reference; implementation cleanup may leave temporary bytes. Partial/uncommitted streams are never returned by Open. Crash during streaming may lose the uncommitted tail; logs needing bounded tail loss can publish immutable chunks and append their references in fenced transactions. An artifact reference does not grant authority to mutate Work.

Artifacts are not transactionally durable with SQLite. A backend must state filesystem flush/publish guarantees and whether power failure can lose a recently published file; the file artifact store states its guarantees in [SQLite and artifacts](../sqlite-artifacts/#artifact-publication-and-integrity). Missing/retained-away content is a reported artifact error and must not invalidate coordination history. Retention deletes content only after policy has released live references (or explicitly recorded expiration); it preserves run metadata and never deletes active writers.

The local coordination schema is version **1**, recorded durably in backend metadata on creation. The Go API and schema version are separate. Every backend exposes its actual persisted schema when opened (`Database.SchemaVersion`). Older binaries refuse newer schemas with an actionable error (`storage.ErrSchemaNewer`), without modification. Future upgrades require explicit ordered transactional migrations and fixture/reopen tests. No automatic downgrade or destructive reset.

Records are stored as JSON and every write re-encodes a record through the writing binary's own structs, so a binary drops any field it doesn't know from each record it rewrites. Adding a field therefore needs no schema migration but does change the record format: the SQLite backend records the highest `RecordFormat` that has opened the database in its metadata (`record_format`; a database without the entry is format 1) and refuses, before changing anything, a database whose format is newer than its own (`storage.ErrRecordsNewer`, `state check`: `records_newer`). Rolling back after a release that added a field is then a restore of the bundle taken before the upgrade, never a silent loss of the new fields. `TestRecordFieldsArePinned` lists every field of the stored records against the format, so a field change fails until it comes with a `RecordFormat` bump.

Back up a consistent snapshot taken by the backend (`Database.Snapshot`; SQLite uses its online backup API) (not an arbitrary live file copy), plus committed referenced artifacts and schema/build metadata. Capture durable references from that snapshot, hold their artifacts from retention while copying (a hold committed before the snapshot), verify them, then publish a complete backup manifest. A partial backup is not a restore point. Restore into a stopped, isolated data directory, validate version/integrity/references, and fence/recover old leases before any executor can commit. The contract permits a backup to omit explicitly expired artifacts if it records the omission; `internal/backup` omits the references of Executions whose retention expired and lists them in the manifest, and any other missing referenced content fails the backup. The operator commands are `open-conduit backup create|verify|restore` ([backup bundles](../backup-bundles/), [recovery](../recovery/)). Never run both runtimes as owners of one scope.

## Backend lifecycle

A `storage.Store` says what open state does; `storage.Backend` ([`storage/backend.go`](https://github.com/open-conduit/open-conduit/blob/main/storage/backend.go)) says how a backend gets it, so the host and `internal/backup` never name a particular backend (#767). A *location* names one instance of a backend's state in its own terms (SQLite's is a file path, a networked backend's would be a connection string), and the host passes it through without interpreting it.

- `Backend.Present(ctx, location)` reports whether state exists there, creating nothing; the offline commands use it so they never make empty state.
- `Backend.Open(ctx, location)` opens the state, creating it when absent. `Backend.Inspect(ctx, location)` opens it for reading only and changes nothing, not even the record format a newer binary would read; it refuses absent state. Both refuse state a newer binary wrote, with `storage.ErrSchemaNewer` or `storage.ErrRecordsNewer`, **before** changing anything at the location, so the newer binary or a restore can still use it.
- `Open` and `Inspect` take exclusive ownership of what the location names, held until `Close`, and refuse state another owner holds with `storage.ErrInUse`, in the same process or any other. The ownership covers the location wherever it is (SQLite locks `<path>.lock` beside the database; a networked backend would take an advisory lock on its server), so two state directories or hosts naming the same state cannot both run as its owner, which the state directory's own `daemon.lock` cannot guarantee once the location may be elsewhere. A location a backend cannot resolve the same way from every process, such as a relative path, is refused with `storage.ErrInvalid`.
- `Database.Snapshot(ctx, path, read)` publishes a complete, verified copy of committed state as a file at an absent path, and calls `read` once, read-only, over exactly the state it copied. A backup reads the references it must copy through `read`, so a write committed after the snapshot is in neither.
- `Backend.Restore(ctx, snapshot, destination, now)` publishes a snapshot at an absent destination, never over existing state, with every Execution lease fenced before the restored state can be opened.
- `Backend.ReadSnapshot(ctx, snapshot, now, read)` calls `read` once over the state `Restore` would publish, raised to this binary's versions, and publishes nothing. A restore checks the bundle's references this way first, because a database on a server is a destination it could not take back.
- `Database.Fence(ctx, now)` is that fence on open state: it clears every lease's owner and expiry and keeps its epoch, so no earlier holder can commit and the next Claim advances the epoch. It is a contract operation so that a standby taking over the state can end the old primary's authority the same way ([#693](https://github.com/open-conduit/open-conduit/issues/693)).
- `Backend.OpenPrior(ctx, location)` holds state an older binary wrote, under the same ownership as `Open`, without changing it, and returns nothing when `Open` would raise nothing (absent, current or newer state). Its `Stored` gives the schema and record format, and its `Snapshot` copies the state at those versions, so the daemon can [keep a bundle before an upgrade](../recovery/#the-bundle-taken-before-an-upgrade).
- `Backend.Writes()` is the schema and record format this binary writes, and `Stored(ctx)`, on an open `Database` or an `Inspection`, the versions the state is at. A bundle records the second and is [refused from its manifest](../backup-bundles/) when it is above the first.
- `IntegrityCheck(ctx)` examines the whole of the stored state, on an open `Database` or an `Inspection`.

A backend registers itself under a name with `storage.RegisterBackend` from its package's `init`, so building its package into the binary is enough to offer it; SQLite registers as `sqlite`. The composition root (`internal/bootstrap/coordination.go`) selects one from the state directory's `storage.json`:

```json
{"backend": "sqlite", "location": "/srv/open-conduit/conduit.db",
 "artifacts": {"backend": "files", "location": "/srv/open-conduit/artifacts"}}
```

`location` is optional and defaults to `<state>/conduit.db`; without the file the directory is SQLite at `conduit.db`, as every state directory was before backends had names. The choice lives in the state directory rather than the config file because config generations are stored in the coordination state itself, and because the offline state commands (`backup`, `state check`, `auth recover`) have only the directory. An unknown backend, an unknown field or a missing name stops the daemon and every offline command; nothing falls back to SQLite, which would start an empty state beside the real one. A backup bundle records its backend in the manifest (omitted for SQLite, so older binaries still read SQLite bundles), and a restore uses that backend and writes `storage.json` into the staged directory when it is not the default, so the directory is published with its storage choice or not at all.

`artifacts` chooses the artifact backend the same way: `backend` names a backend registered with `storage.RegisterArtifactBackend` and `location` is handed to it verbatim, defaulting to `<state>/artifacts`. Without `artifacts` the store is the file store, `files`, at `<state>/artifacts`. The daemon, `backup create` and `state check` open the store through `storage.LookupArtifactBackend`, and `state check` names the backend in its `artifacts` line. An unknown artifact backend, an unknown field or a missing name stops the daemon and `backup create` and fails `state check`; nothing falls back to the file store, which would start an empty store beside the real one. A binary from before artifact choices refuses a `storage.json` that has one as an unknown field, for the same reason. A bundle's own artifacts are always a file store, since they are part of the bundle format. `backup restore` imports them into the file store in the restored directory, or into the backend and location the operator names (`--artifacts NAME --artifacts-location LOC`), and then records that choice in the staged directory's `storage.json` ([backup bundles](../backup-bundles/#restoring-a-bundle)).

**Where a backend lives.** A backend is a Go package compiled into the binary, not an out-of-process provider. `Transact` runs the runtime's callback inside one serializable transaction, so a process boundary between the runtime and the backend would put a round trip on every read of every transaction, and a networked backend's database is already its own process. A backend that needs third-party modules (a Postgres driver, say) lives in its own package, in-tree behind a build tag or in its own module, and is built in by a `cmd/open-conduit` file that imports it under that tag; `storage`, `runtime` and the default build stay free of third-party modules. It reaches the host only through the public contract and the registry, as SQLite does, so nothing about a bundled backend is privileged. Running the storage and lifecycle suites is what makes it one. An artifact backend lives the same way, and runs the artifact suite (`conformance.RunArtifacts`). It could cross a process boundary at less cost than coordination, since nothing waits on it inside a transaction, but the offline commands open the store with only the state directory to go on, before any extension package could start, so a built-in one is compiled in too ([#775](https://github.com/open-conduit/open-conduit/issues/775)).

**An artifact store from outside the binary.** An artifact backend can also run as its own process, so S3, GCS or any other store can be installed without changing or rebuilding Open Conduit ([#695](https://github.com/open-conduit/open-conduit/issues/695)). A provider is an executable whose `main` calls [`artifactstore.Serve`](https://github.com/open-conduit/open-conduit/blob/main/protocol/artifactstore/artifactstore.go) with its `storage.ArtifactBackend`, and it proves itself with `conformance.RunArtifacts` like any other backend. `storage.json` names it:

```json
{"backend": "sqlite", "artifacts": {"backend": "s3", "command": "/usr/local/bin/oc-s3", "location": "s3://bucket/prefix"}}
```

`command` is an absolute path and `location` is required and passed through uninterpreted. The name can't be a built-in backend's. The daemon and the offline commands all read this file, so each starts the provider itself. The provider speaks the [artifact provider protocol](../artifact-providers/) on stdin and stdout, so it can be written in any language, logs to stderr, inherits the host's environment (which is how it gets cloud credentials) and runs with the host's privileges. A bundle never carries a command: only the operator's `--artifacts-command` on a restore writes one. The host verifies what crosses the boundary: it computes the size and digest of everything written and read, refuses a commit whose ref doesn't describe the content, and treats a read that doesn't match as `ErrCorrupt`. A provider that dies is started again on the next call, and only the streams open in it fail.

The routing, wait and recovery rules in [B04](../runtime-semantics/) (successor identity, ordered multi-key attachment, subscription aliases, timeout arbitration, retry eligibility and causal bounds) apply above the storage boundary; Claim alone does not enforce eligibility.

A backend whose state another system replicates continuously can also implement `storage.ReplicaRestorer`: `RestoreReplica` publishes what that system kept at an absent destination, verified and fenced as `Restore` does a snapshot, without changing the replica ([restoring from a replica](../recovery/#restoring-from-a-replica)).

## Evidence

Run `go test -race ./...` and `go vet ./...` from the repository root; no external service is needed.

The shared storage scenarios (`conformance.StorageCases`) exercise delivery identity versus correlation, route replay, atomic route effects, revisions/copy isolation, concurrent key ownership and claims, lease expiry/recovery/renew/release, cancellation fencing, timer rollback/one-shot/recreation, wait park/wake and timer cancellation, KV checkpoints, cancellation/panic rollback, parent cycles, attempt exhaustion, handoff/wait outcomes, per-Work order, recovery inventory, live reads, Work and scope event reads, Work queries, views alongside writes, finished attempts' artifacts and the artifacts attempts reference, and the guarantees a backend with concurrent writers has to keep on purpose: sequences visible in sequence order, KV keys compared as bytes, and transient aborts that commit nothing. They run against the reference double and against SQLite. Lifecycle tests cover all state pairs, including unknown/terminal states. Negative controls select the actual shared cases and require the expected failure diagnostic for broken deduplication, atomicity and the other weakened backends each case names, without making the test invocation fail intentionally.

Twelve lifecycle scenarios (`conformance.LifecycleCases`, run by `conformance.RunLifecycle` with a `LifecycleHarness` that ages, fingerprints and corrupts the backend's stored state) exercise open and reopen, a presence check that creates nothing, one owner at a time, refusal of a newer schema and of newer records with the state unchanged, an inspection that reads and changes nothing, older state preserved unchanged, a consistent snapshot that restores and never overwrites, a snapshot read that sees the state and publishes nothing, a restore that fences every lease, a fence on open state, and an integrity check that finds damage `Open`'s quicker check misses. They run against SQLite, and `TestWeakenedLifecycleIsRejected` requires the expected failure from each of ten weakened SQLite backends: a snapshot read that sees other state, one that changes the snapshot, an open that shares its location, a presence check that reports absent state, a restore that leaves a lease live, an open that accepts newer records, an open that writes before refusing, a preservation that raises the format first, a fence that does nothing and an integrity check that passes anything.

Ten artifact scenarios (`conformance.ArtifactCases`, run by `conformance.RunArtifacts` with an `ArtifactHarness` that damages stored bytes in place) exercise a commit's size, media type and digest, an abort that publishes nothing, no reads or listing of uncommitted content, commit and close happening once, `Open` refusing a reference that doesn't match, reads that verify the size and digest, committed content surviving a reopen while an unfinished writer leaves nothing, idempotent delete that checks the reference, listing every committed artifact once in ID order, and an import that publishes exactly its reference or nothing. The file artifact store runs them, and `TestWeakenedArtifactsAreRejected` requires the expected failure from seven weakened file stores: a commit that drops the digest, an abort that publishes, an open that ignores the digest, a reader that trusts damaged bytes, a delete that reports missing content, a list that pages out of order and an import that ignores the digest.

Passing the memory double proves reference semantics only. SQLite transaction isolation, crash durability, WAL/reopen/backup and competing connections are proved by the SQLite backend's own tests ([SQLite and artifacts](../sqlite-artifacts/#evidence)).
