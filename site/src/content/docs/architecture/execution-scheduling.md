title: "Execution scheduling, recovery and control"
description: "How Open Conduit starts, recovers, retries and controls execution attempts under B04 policy."
---

The scheduler starts execution attempts for ready Work, recovers them after lost authority, applies retry policy and dispatches inject/interrupt controls. It implements [B04 execution policy](../runtime-semantics/) over the public storage and executor contracts. [The scheduler](https://github.com/open-conduit/open-conduit/blob/main/internal/runtime/scheduler.go), [retry policy](https://github.com/open-conduit/open-conduit/blob/main/internal/runtime/scheduler_policy.go) and [control dispatch](https://github.com/open-conduit/open-conduit/blob/main/internal/runtime/scheduler_control.go) compose with the production [router](../routing-lifecycle/). They contain no process, service, SQLite or configuration-loader dependency. A host drives these operations: in the daemon, the host loop in [`internal/bootstrap`](https://github.com/open-conduit/open-conduit/tree/main/internal/bootstrap) starts ready Work, observes attempts, renews leases, dispatches controls and confirms physical stops ([daemon](../daemon-core-gate/)).

## Starting attempts

`NewScheduler(store, now, router, options)` takes a trusted clock, owner, configuration generation and mechanically validated executor registrations. Defaults are four concurrent attempts, a one-minute lease, a one-hour execution timeout and three total failure attempts. Scope limits apply to the selected scope and its ancestors. Constructor options are copied. Binding inheritance resolves before claim; the commit rechecks Work, input and Scope snapshots.

`Start` atomically selects ordered pending input, creates the next monotonic attempt, claims its lease, pins behavior and records consumed-input history. The durable launch intent precedes `Run`. Executor calls, capability methods and retry-hint callbacks run outside coordination transactions; a blocked executor cannot retain the storage lock. No process-local global lock coordinates claims. Real serializable storage prevents competing schedulers from creating simultaneous attempts or exceeding configured capacity.

The attempt snapshot retains its configuration generation, full binding, executor registration, capabilities, retry policy, timeout deadline, control error fallback and handoff policy. `HistoricalExecutors[generation][registration]` must reinstall the exact older implementation for recovery/control after reload. A missing generation is unsupported; it never selects a replacement executor silently. Future attempts use current validated bindings and policy. Secret resolution and authorization ceilings belong to the [configuration](../config-management/) composition, not the scheduler; secrets are not part of durable attempt snapshots. The same goes for the run environment layer: `SchedulerOptions.Environment` asks the extensions of the attempt's scope for it (`extension.RunEnvironment`) before `Run` and `Resume`, never for a recovery, and puts it in `ExecutionContext.Env`. It is never persisted, and a failure fails the attempt as `run environment unavailable` (`ErrEnvironmentUnavailable`) before the executor is called.

A binding may set `timeout_seconds`, which replaces `SchedulerOptions.Timeout` for its attempts (pinned with the binding in the attempt state; a resumed segment keeps its remaining budget). When a Work opted into [binding grants](../config-management/#binding-grants), the binding the attempt pins already has their config applied, and the attempt state's `Grants` names the ones it took, so recovery and resume keep them.

`SchedulerOptions.WorkKinds` registers an extension's lifecycle policy for the Work kind it creates. `Standing` Work returns to ready (idle) after a completed attempt and arms no automatic retry after a failed one; `RunOnce` Work does all its work in one attempt, so an attempt that hands back settles as completed; `Trigger` selects which input of the pending batch triggers the attempt. Scheduled jobs use both for the one-pending-run rule ([runtime semantics](../runtime-semantics/#pending-job-coalescing-and-standing-work)).

## Attempt segments

The attempt state keeps the attempt's segments, the stretches it held a lease, measured exactly as the timeout budget measures them. `Start` begins one in its claim transaction: the first start, or a resume of a parked attempt, carrying the wake's event ID when a wake started it. A resume wait's registration ends the open segment in the park transaction, where the remaining budget is stored. `Recover` ends the open segment and begins one marked `recovered` at the same instant, with no gap. Recovery keeps the deadline, so the budget charges the time between a lost lease and its recovery, and the segments charge it too. This holds whether the lease expired after a crash or `Release` cleared it in a graceful stop. A timeout processed after the lease expired recovers first, so it leaves a zero-length `recovered` segment. Every other end, a non-resume wait included, is the execution's terminal finish, which the history record uses to close the last segment. While an attempt is parked, its ended segments and its remaining budget sum to its timeout.

An attempt keeps its last 50 segments (`MaxSegments`), with the count and active time of the dropped ones accumulated. An attempt started before segments were recorded gains none, so its history shows no segments rather than a partial record. Segments are lease-held time, not proof that a process ran: an adopted detached process may have run through the gap, and an attempt that crashed between claim and launch held a lease without running.

## Recovery and resource exclusion

`Start` and `Recover` return an `Attempt` containing its lease, request and handle. An executor must successfully use the fenced `PersistRecovery` callback before returning a successful handle. The scheduler validates bounded opaque JSON recovery metadata and checks current authority around launch acknowledgement. Missing acknowledgement or an ambiguous operation records a safe failure and retains resource exclusion. Executors own closing the process launch/persist crash window through deterministic discovery, prelaunch intent or cleanup, as required by B03.

`Recover` claims the same nonterminal attempt at a higher epoch and persists recovery-in-progress before calling `Recover` outside storage. It never calls `Run` to replace that attempt. An unapplied toolbelt declaration carries over to the new epoch. Renew/release use the exact lease; release makes that same attempt recoverable. Old outcomes, metadata callbacks and renewals fail after expiry, release, cancellation or a newer epoch. Observation cancellation cancels `Wait` observation only and does not assert that a detached process stopped.

Lease fencing and physical resource exclusion are separate. Durable attempt holds survive restart, including terminal attempts with uncertain external processes, and count against Work/global/ancestor capacity. `ErrNotAdoptable`, transport errors, timeout and a successful interrupt request do not prove that resources stopped. Replacement remains blocked until the trusted host supplies `ConfirmStopped(executionID, expectedEpoch)`. A successfully observed structured terminal result establishes finished attempt resources. Confirmations cannot target an attempt that has since been adopted at another epoch. A binding's sandbox ([B09](../sandboxes/)) is bound by `SchedulerOptions.Sandbox` beside the resource; its plan's digest is pinned with the open segment (`Segment.Sandbox`) through a lease-fenced callback, and a recovered segment carries it. The generic scheduler does not inspect process IDs or executor metadata: the [shell executor](../shell-executor/) supplies verified-stop evidence through `Stop(execution, epoch)`, and the [daemon](../daemon-core-gate/) renews observed leases and performs that stop/confirm after lost authority, observation failure or a failed recovery.

## Outcomes, handoff and retry

`Observe` waits outside storage, then applies a lease-fenced structured result. Completed Work cannot overtake accepted unrouted input; queued or unconfirmed injected input leaves it ready for N+1. Results preserve common outcome, usage and artifact-reference history. Failed attempts return Work to ready with bounded retry eligibility, unless an explicit terminal-on-exhaustion policy fails Work. An executor whose handle fails with an `extension.OperationError` leaves its code and message on the failed attempt's summary (`executor observation failed: <code>: <message>`, `runtime.FailureCause`), and the host's `observe` diagnostic logs it as `cause`; any other executor error's text is kept out, since it may carry provider output. `Timeout` requires the persisted deadline to be due and current lease authority, then records failure and retains the uncertain resource hold. A host must recover expired authority before applying such a mutation; a clock deadline does not grant a stale lease authority.

An outcome whose data declares a turn (`core.turn.v1` `{status, comment}`, `status` one of `building`, `review`, `help`, `done`, `finished`; for one release also the source-named `<source>.status.v1` that stored outcomes keep) publishes a `core.execution.turn` Event in the transition that stores it, whatever the outcome kind: one per correlation key of the Work (one without a key for keyless Work), derived from the attempt's trigger, with payload `core.execution.turn.v1` `{status, work, execution}` and delivery `turn/<execution>/<lease epoch>[/<key>]`, so a repeated transition is a no-op and a resumed attempt's next turn is a new Event. It is recorded as unmatched, never input: another Work's dependency subscription on the key is what it is for, and a Work's own turn never wakes its own Wait. Causal refusal skips it and keeps the outcome.

Handoff ends the attempt and leaves Work ready for eligible input. Automatic continuation is off by default. If explicitly enabled, a stable derived `core.execution.handoff` Event and queue checkpoint join the outcome transaction. Causal refusal records a diagnostic and stops that continuation branch while preserving the handoff outcome. A bare waiting outcome cannot bypass event-based suspension; predicate registration, structured waiting results and fenced acknowledgement are described in [timers and waits](../timers-waits/).

Failures arm a durable retry Timer template with the failed attempt generation and trigger ancestry. Default delays are five and ten minutes; an explicit four-attempt policy adds fifteen minutes. Failure counts are separate from attempt numbers. Up to 100 configured delays yield 101 total attempts, matching the B05 schema. Generic retry hints select reset time plus two minutes, or thirty minutes for an unknown reset; invalid/past/excessive hints fail explicitly. Hinted failures still consume the bounded failure budget. Provider classification stays outside core.

An executor's retry hint also applies to standing Work: a hinted failure arms the retry timer and blocks scheduling until it fires, without exhausting the Work, while a hintless failure of standing Work arms nothing. A hint's delay does not index the failure-budget delays, so a standing Work with many failures cannot overrun them.

Executor errors implement the optional public `extension.RetryHintProvider`; they do not import runtime implementation types. `Complete`/`Fail` accept a trusted host's finished structured result. A toolbelt outcome or wait declaration is recorded under the current fence but applied only when the host observes the executor finishing or suspending that segment through `Complete`, so process/resource exclusion is established before replacement capacity is granted; a client declaration alone is not stop evidence.

`ProcessRetry` consumes an already accepted trusted retry Event. The timer driver must first accept through `AcceptDerivedInTx` and atomically remove/fire the timer. A due clock alone never clears eligibility. `core.retry.requested` (B04) and `core.manual.retry` (B05) are manual aliases. The event must follow the current failure's acceptance-sequence boundary, and a processed Event cannot clear a later failure. Manual retry resets the automatic failure budget, not attempt numbering. Old due generations, terminal Work and replay remain historical; live attempts/Waits prevent retry. Ordinary queued input during backoff does not clear it.

## Control dispatch

`DispatchControl` claims a durable intent, performs `Inject`/`Interrupt` outside storage, and acknowledges only with the same live dispatch token. It uses the pinned attempt executor, capabilities, target and epoch. A new executor registration cannot grant control capability to an older attempt. Inject acknowledgement means accepted, not consumed: pending input remains eligible for subsequent presentation. Ambiguous delivery retries the same intent/Event identity, with no exactly-once transport promise. An explicit pinned queue/drop error fallback is recorded; provider error text is not persisted. Late acknowledgements, completed targets and superseded epochs cannot retarget a newer attempt. An `ErrNotAccepting` answer settles the intent as `not_accepting` (no retry, input retained). A result's `ConsumedInputs`, on any outcome and even while the dispatch acknowledgement is in flight, settles it as `consumed` ([generic inject acknowledgement](../runtime-semantics/#generic-inject-acknowledgement)).

Interrupt fences the old attempt and leaves Work ready before sending control, but retains its resource hold until stopping is verified. Work cancellation atomically fences attempts, Waits, owned timers and queue eligibility through the router. Physical cleanup follows that commit. The host must not treat acknowledgement of a stop request as proof of resource exclusion.

## Capacity pools

Capacity is split by executor, so scheduled jobs and agent turns do not take slots from each other. `SchedulerOptions.ExecutorPools` gives an executor registration its own pool, bounded by `PoolLimits[pool]`; an executor without a pool counts against `GlobalLimit`. An attempt counts only against its own pool, and `Start` refuses with a `CapacityError` (it matches `ErrCapacity`) naming the full pool, or the scope for a scope limit. Scope limits still count every pool.

The daemon puts the job executors (`shell`, `github-hold`) in the `jobs` pool, bounded by `settings.job_concurrency` (default 4). `settings.concurrency` (default 4) then bounds agent turns (`claude-code`) and installed extension executors. With the agent limit reached a due job still starts, subject to `job_concurrency`, and the reverse holds. A job and a turn can run at once up to the sum of the two limits. A config that relies on `concurrency` to bound jobs as well should add `job_concurrency`. An agent job (a `claude-code` binding selected by a `schedule` route) is an agent turn and counts against `concurrency`.

A scope's `limits.concurrency` narrows this further: the daemon passes each scope whose limit is below its parent's (or `settings.concurrency` at the root) as `ScopeLimits`, and the scheduler checks the attempt's scope and every ancestor, counting attempts from both pools.

A start held back by a limit is reported with the code of its setting: `capacity_concurrency`, `capacity_job_concurrency` or `capacity_scope`. `open-conduit doctor` has a `capacity` check: each pool's running attempts against its limit, and each ready Work waiting for one with the limit holding it back. The Work's detail (`GET /v1/work/{id}`, the CLI and the TUI) carries a `waiting` annotation with the same limit. `GET /v1/capacity` gives the same accounting to clients: for each pool (`agents` for `settings.concurrency`, `jobs` for `settings.job_concurrency`), its `limit` (zero: unbounded), the attempts holding a slot (`in_use`) and the ready Work its limit held back (`waiting`). Work held back by a scope limit counts in no pool. `in_use` is read from storage on each request. `waiting` is the daemon's process-local result of its last start pass, so it reads 0 after a restart until the first pass, and for one pass it can disagree with `in_use`. Ready Work skipped as idle (no pending input) is cleared from it.

## Evidence

[SQLite scheduler tests](https://github.com/open-conduit/open-conduit/blob/main/internal/runtime/scheduler_test.go) run eleven applicable shared runtime cases through the production scheduler with persistent and independently reopened handles. A small explicit timer-contract adapter accepts the retry Event and fires its stored timer for these tests. Additional cases cover blocked Run progress, global/scope/ancestor capacity, same-attempt recovery, stale callbacks, uncertain-launch restart, resource holds, cancellation orders, inject/completion races, interruption, deadlines and handoff. [Policy regressions](https://github.com/open-conduit/open-conduit/blob/main/internal/runtime/policy_test.go) cover generation-pinned retry/capabilities, missing launch acknowledgement, retry bounds and explicit control error policies. [`TestProductionSchedulerExecutorPools`](https://github.com/open-conduit/open-conduit/blob/main/internal/runtime/scheduler_test.go) and [`TestDaemonJobConcurrency`](https://github.com/open-conduit/open-conduit/blob/main/integration/daemon_schedule_test.go) cover capacity pools.
